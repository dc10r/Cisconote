<h2>BGP Path Vector Characteristics</h2>

The main goal of BGP is to provide an interdomain routing system that guarantees the loop-free exchange of routing information between autonomous systems. BGP routers exchange information about paths to destination networks

BGP allows routing-policy decisions to be applied to the path of BGP autonomous system numbers so that routing behavior can be enforced at the autonomous system level and to determine how data will flow through the autonomous system.

The policies are based on the attributes carried in the routing information and configured on the routers.

BGP specifies that a BGP router can advertise to its peers (neighbors) in neighboring autonomous systems only those routes that it uses. 

BGP (and hop-by-hop routing in general) treats routing decisions as per-destination, not per-source-and-destination. Every router picks one path to each destination and applies it uniformly, regardless of who sent the traffic or where it came from. This keeps routing scalable and simple, but it also means certain fine-grained policies — like "let different senders take different paths to the same place" — simply can't be expressed or enforced within standard BGP.

<h2>BGP Characteristics</h2>

BGP is a path vector protocol. 

BGP uses the Transmission Control Protocol (TCP) as its transport protocol, which provides connection-oriented reliable delivery. assuming that its communication is reliable and, therefore, BGP does not have to implement any retransmission or error-recovery mechanisms, like EIGRP does. 

BGP information is carried inside <b>TCP</b> segments using protocol <b>179</b>

Two routers speaking BGP (called BGP speakers ) establish a TCP connection with one another and exchange messages to open and confirm the connection parameters. These two routers are called BGP peer routers or BGP neighbors 

After the TCP connection is made, the routers exchange their full BGP tables, because the connection is reliable, BGP routers need to send only changes (incremental updates) after that. BGP sends keepalive messages.

BGP keeps a
<ul>
  <li>neighbor table containing a list of neighbors with which it has a BGP connection.</li>
  <li>own table for storing BGP information received from and sent to other routers.</li>
</ul>

It is important to remember that this BGP table is separate from the IP routing table in the router.

The router offers the best routes from the BGP table to the IP routing table. By redistribution it and can be configured to share information between the two tables.

<h2>BGP Routing Process</h2>

<ul>
  <li>For BGP to establish an adjacency, you must configure it explicitly for each neighbor.</li>
  <li>BGP forms a TCP relationship with each of the configured neighbors, keeps track of the state of these relationships by periodically sending a BGP/TCP keepalive message.</li>
  <li>After establishing an adjacency, the neighbors exchange their best BGP routes.</li>
  <li>Each router collects these routes from each neighbor with which it successfully established an adjacency, places them in its BGP table; all routes that have been learned from each neighbor are placed in the BGP table</li>
  <li>Each path learned is associated with BGP attributes.</li>
  <li>The single best route for each network is selected from the BGP table using these attributes in the BGP route-selection process and then offered to the IP routing table. </li>
  <li>Each router compares the offered BGP routes to any other possible paths to those networks in its IP routing table, and the best route, based on administrative distance,(<b>Lower administrative distance wins</b>), is installed in the IP routing table. </li>
  <li>External BGP (eBGP) routes (BGP routes learned from an external autonomous system) have a default administrative distance of 20. </li>
  <li>Internal BGP (iBGP) routes (BGP routes learned from within the autonomous system) have a default administrative distance of 200.</li>
  <li>A router may have a best BGP route to a destination, but that route might not be installed in the IP routing table because it has a higher administrative distance than another route. </li>
  <li>That best BGP route will still be propagated to other BGP routers, though.</li>

</ul>

<h2>Open and Keepalive Messages</h2>

TCP connection(established) -> each side sends open message -> Keepalive sent confirming open (Sent by receiver, if open acceptable) -> BGP connection is established (peers exchange their full BGP routing tables) 

<ul>
  <li>1 -> incremental updates are sent as the table changes. </li>
  <li>2 -> Keepalive packets are sent to ensure the connection is alive</li>
  <li>3 -> notification packets are sent in response to errors or special conditions.</li>
</ul>

After a TCP connection is established, the first message sent by each side is an open message. 

If the open message is acceptable, a keepalive message confirming the open message is sent back by the side that received the open message.

When the open is confirmed, the BGP connection is established, and update, keepalive, and notification messages can be exchanged.

BGP peers initially exchange their full BGP routing tables. 

incremental updates are sent as the table changes. 

Keepalive packets are sent to ensure that the connection is alive between the BGP peers, and notification packets are sent in response to errors or special conditions.

<h2>BGP Neighbor States</h2>

BGP is a state machine that takes a router through the following states with its neighbors:

<ul>
  <li>Idle</li>
  <li>Connect</li>
  <li>Active</li>
  <li>Open sent</li>
  <li>Open confirm</li>
  <li>Established</li>
  <li>Only when the connection is in the established state are update, keepalive, and notification messages exchanged.</li>
</ul>

<h2>When to Use BGP</h2>

BGP use in an autonomous system is most appropriate when the effects of BGP are well understood and at least one of the following conditions exists:

<ul>
  <li>The autonomous system allows packets to transit through it to reach other autonomous systems (for example, it is a service provider).</li>
  <li>The autonomous system has multiple connections to other autonomous systems</li>
  <li>Routing policy and route selection for traffic entering and leaving the autonomous system must be manipulated.</li>
</ul>

<h2>When Not to Use BGP</h2>

Do not use BGP if one or more of the following conditions exist:
<ul>
  <li>A single connection to the Internet or another autonomous system.</li>
  <li>Lack of memory or processor power on edge routers to handle constant BGP updates.</li>
  <li>You have a limited understanding of route filtering and the BGP path-selection process</li>
  <li>If the routing policy that will be implemented in an autonomous system is consistent with the policy implemented in the ISP autonomous system.</li>

</ul>

<h1>Implementing Basic BGP</h1>

<h2>BGP Neighbor Relationships</h2>

A BGP router forms a direct neighbor relationship with a limited number of other BGP routers. Through these BGP neighbors, a BGP router learns of the paths through the Internet to reach any advertised network. Recall that any router that runs BGP is called a BGP speaker. 

A BGP peer, also known as a BGP neighbor, is a BGP speaker that is configured to form a neighbor relationship with another BGP speaker for the purpose of directly exchanging BGP routing information with one another.


BGP peers can be either internal or external to the autonomous system. 

<h3>External BGP Neighbors</h3>

There are several requirements for an eBGP neighbor relationship (also called an eBGP neighborship):

<ul>
  <li>Different autonomous system number - eBGP neighbors must reside in different autonomous systems to be able to form an eBGP relationship.</li>
  <li> Define neighbors - A TCP session must be established before starting BGP routing update exchanges. </li>
  <li> Reachability - The IP addresses used in the neighbor command must be reachable; eBGP neighbors are usually directly connected</li>
</ul>

<h3>Internal BGP Neighbors</h3>

There are several requirements for an iBGP neighbor relationship (also known as an iBGP neighborship):


<ul>
  <li>Same autonomous system number - iBGP neighbors must reside in the same autonomous system to be able to form an iBGP relationship</li>
  <li> Define neighbors - A TCP session must be established between neighbors before they start exchanging BGP routing updates </li>
  <li> Reachability - iBGP neighbors must be reachable. An IGP typically runs inside the autonomous system, and provides this reachability</li>
</ul>

<h2>iBGP in a Transit Autonomous System</h2>

A transit autonomous system is an autonomous system that routes traffic from one external autonomous system to another external autonomous system (Transit autonomous systems are typically ISPs.). All routers in a transit autonomous system must have complete knowledge of external routes. 

One way to achieve this goal is to redistribute BGP routes into an IGP at the edge routers; however, Because the current Internet routing table is very large, redistributing all the BGP routes into an IGP is not a scalable. Another method that you can use is to run iBGP on all routers within the autonomous system.

A nontransit autonomous system, such as an organization that is multihoming with two ISPs, does not pass routes between the ISPs. To make proper routing decisions, the BGP routers within the autonomous system still require knowledge of all BGP routes passed to the autonomous system.

Because the designers of BGP could not guarantee that an autonomous system would run BGP on all routers. a method had to be developed, ensure that iBGP speakers could pass updates to one another while ensuring that no routing loops would exist.

<h2>TCP and Full Mesh</h2>


TCP sessions cannot be multicast or broadcast because TCP has to ensure the delivery of packets to each recipient. Because TCP cannot use broadcasting or multicasting, BGP cannot use it either.

To avoid routing loops within an autonomous system, BGP specifies that routes learned through iBGP are never propagated to other iBGP peers; this is sometimes referred to as the BGP split-horizon rule

An iBGP neighbor relationship must be configured between each pair of routers.

By default, each BGP speaker is assumed to have a neighbor statement for all other iBGP speakers in the autonomous system; this is known as full-mesh iBGP. The neighbor command enables BGP updates between BGP speakers   

When a change is received from an external autonomous system, the receiving BGP router is responsible for informing all of its iBGP neighbors of the change.  iBGP neighbors that receive this update do not send it to any other iBGP neighbor because they assume that the sending iBGP neighbor is fully meshed with all other iBGP speakers and has sent each iBGP neighbor the update.

<h2>Basic BGP Configuration Requirements</h2>

Parameters needed to provide the BGP configuration details. For basic BGP, these details include the following:

<ul>
  <li>The autonomous system numbers (of your own network and of all remote autonomous systems)</li>
  <li>The IP addresses of all the neighbors (peers) involved</li>
  <li>The networks that are to be advertised into BGP
</li>
</ul>

Basic BGP configuration requires the following main steps:

<ul>
  <li>Step 1. Define the BGP process.</li>
  <li>Step 2. Establish the neighbor relationships.</li>
  <li>Step 3. Advertise the networks into BGP.</li>
</ul>

<h3>Entering BGP Configuration Mode</h3> 

Use the <b>router bgp autonomous-system</b> global configuration command to enter BGP configuration mode and identify the local autonomous system in which this router belongs. 

The BGP process needs to be informed of its autonomous system so that when BGP neighbors are configured it can determine whether they are iBGP or eBGP neighbors.

Only one instance of BGP can be configured on a router at a time.

<h3>Defining BGP Neighbors and Activating BGP Sessions</h3>

Use the <b>neighbor ip-address remote-as autonomous-system</b> router configuration command to activate a BGP session for external and internal neighbors and to identify a peer router with which the local router will establish a session

<h2>Advertising Networks in BGP</h2> 

Use the <b>network network-number [ mask network-mask ]</b> router configuration command to inject routes that are present in the IPv4 routing table into the BGP table so that they can be advertised in BGP.

the BGP network command determines which networks this router advertises. The network command does not start BGP on specific interfaces. Rather, it indicates to BGP which networks it should originate from this router.

The list of network commands must include all networks in your autonomous system that you want to advertise, not just those locally connected to your router.

The mask parameter indicates that BGP-4 allows classless prefixes; it can advertise subnets and supernets

the difference between the neighbor command and the network command: The neighbor command tells BGP where to advertise; the network command tells BGP what to advertise

If the mask parameter is not specified, this command announces only the classful network number; at least one subnet of the specified major network must be present in the IP routing table to allow BGP to start announcing the classful network as a BGP route. If the mask network-mask is specified, an exact match to the network (both address and mask) must exist in the routing table for the network to be advertised.

Before BGP announces a route, it checks to see whether it can reach it.


<b>can configure a static route toward the null interface, with the ip route 192.168.0.0 255.255.0.0 null0 command</b>

<h3>Examining the BGP Table</h3> 

A row with an asterisk (*) in the first column means that the next-hop address is valid.

A greater-than sign ( > ) in the second column indicates the best path for a route selected by BGP. This route is offered to the IP routing table

The third column is either blank or has an i in it. If it is blank, BGP learned that route from an external peer. If it has an i , an iBGP neighbor advertised this route to this router.

The fourth column lists the networks that the router learned.If this column contains 0.0.0.0, this router originated the route.

The next three columns list three BGP path attributes associated with the path: metric, which is also called the multi-exit discriminator (MED); local preference; and weight.

The column with the Path header may contain a sequence of autonomous systems in the path. From left to right, the first autonomous system listed is the adjacent autonomous system from which this network was learned. If the last column has an i in it, the original router probably used a network command to introduce this network into BGP. 
The character e signifies that the original router learned this network from EGP, which is the historic predecessor to BGP. A question mark ( ? ) signifies that the original BGP process cannot absolutely verify this network’s availability because it is redistributed from an IGP into the BGP process.


<h3>Next-Hop-Self Feature</h3>


Every route BGP advertises carries a next-hop attribute: "to reach this destination network, send traffic to this IP address." you'd assume each router along the path updates that IP to point to itself. But BGP doesn't do that automatically for eBGP routes once they enter your AS via iBGP.


by default, BGP doesn't change the "next-hop" address when a route crosses from eBGP into iBGP — and that can leave your internal routers unable to actually reach the destination.

You configure next-hop-self on the router facing the external neighbor. This tells the router: "when you advertise this route to my iBGP peers, replace the next-hop with my own address instead of leaving the external one."

Next-hop-self <b> neighbor ip-address nest-hop-self</b> makes the edge router say "route through me" instead of "route through that external IP you've never heard of." It's typically applied on eBGP-facing routers when advertising routes onward to iBGP peers, specifically to avoid next-hop unreachability inside the AS.


<h3>Understanding and Troubleshooting BGP Neighbor States</h3>

After the TCP handshake is complete, the BGP application tries to set up a session with the neighbor. BGP is a state machine that takes a router through the following states with its neighbors:


<ul>
  <li>Idle - The router is searching the routing table to see whether a route exists to reach the neighbor.</li>
  <li>Connect - The router found a route to the neighbor and has completed the threeway TCP handshake.</li>
  <li>Open sent - An open message was sent, with the parameters for the BGP session.</li>
  <li>Open confirm - The router received agreement on the parameters for establishing a session. Alternatively, the router goes into the active state if there is no response to the open message.</li>
  <li>Established - Peering is established and routing begins</li>

</ul>

<h3>idle state</h3> 

After you enter the neighbor remote-as command, BGP starts in the idle state, and the BGP process checks that it has a route to the IP address listed. 
BGP should be in the idle state for only a few seconds. 
However, if BGP does not find a route to the neighboring IP address, it stays in the idle state.

<h3>connect state </h3>
If it finds a route, it goes to the connect state when the TCP handshaking synchronize acknowledge (SYN ACK) packet returns (when the TCP three-way handshake is complete). After the TCP connection is set up, the BGP process creates a BGP open message and sends it to the neighbor. 


<h3>open sent state</h3>
After BGP dispatches this open message, the BGP peering session changes to the open sent state. 

<h3>active state</h3>

If there is no response for 5 seconds, the state changes to the active state. 


<h3>open confirm state </h3>
If a response does come back in a timely manner, BGP goes to the open confirm state and starts scanning (evaluating) the routing table for the paths to send to the neighbor. 


<h3>established state </h3>

When these paths have been found, BGP then goes to the established state and begins routing between the neighbors.

<h3>BGP Session Resilience</h3> 

In cases where multiple paths exist to reach an iBGP neighboring routers, the routers could peer with each other’s loopback interface address and the BGP session would not be lost because loopback interfaces are always available as long as the router itself does not fail. 

This peering arrangement adds resiliency to the iBGP sessions because they are not tied into a physical interface, which might go down for any number of reasons.

<h3>Sourcing BGP</h3> 

<b>neighbor ip-address update-source <interface></b> 

when a router initiates a BGP TCP connection to a neighbor, it uses the outgoing interface's IP address (the interface closest to that neighbor, based on the routing table) as the source address for the packets. This works fine for most eBGP sessions, where two routers are directly connected via a single physical link — there's only one obvious interface to use.

Because most networks have multiple physical paths between internal routers (for redundancy). If you instead peer via loopback addresses, the BGP session stays up as long as any path to the router exists, since the IGP (like OSPF) can route around a failed link to reach the loopback.

So neighbor ip-address update-source loopback0 tells the router: "When you open this BGP session, use my loopback0 interface's IP address as the source, not whatever physical interface happens to be in the path."
