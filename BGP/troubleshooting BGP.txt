By default, an EBGP peering occurs between directly connected routers. This means the routers forming the EBGP peering are expected to be within one router hop of each other.


With an IBGP peering, the routers can be up to 255 router hops from each other and still form a peering. The output of <b>show ip bgp neighbors 172.16.4.4 | include BGP neighbor|TTL</b> displays that BGP is checking for directly connected EBGP neighbors and that the current EBGP has failed that check. If the external neighbor is not reachable within 1 hop, the BGP packet expires, and no neighbor relationship is formed.

<b>
R2(config)# router bgp 65001
R2(config-router)# neighbor 172.16.4.4 ebgp-multihop 2
</b>

Entering the ebgp-multihop command with a TTL value of 2 (or more) allows the EBGP neighbor relationship to become established.


As mentioned above, another possible solution would be to use the <b>neighbor disable-connected-check</b> command instead of <b>ebgp-multihop</b>:

<b>
R3# configure terminal 
R3(config)# router bgp 65001
R3(config-router)# neighbor 172.16.1.1 next-hop-self
R3(config-router)# end
R3# clear ip bgp 172.16.1.1 soft out
</b>

R3 will now advertise its IP address as the next-hop for R1 to use for any external networks it learns from R3.

In old BGP designs, redistribution between BGP and an IGP was a common practice, and these protocols had to be synchronized to ensure proper packet forwarding. In modern designs, redistribution is no longer used, and synchronization must be turned off. This type of message is usually generated by a router ACL dropping packets. The ICMP message is being sourced by R7 so the R7 configuration needs to be investigated.


An ACL has been configured inbound on the interface used to reach R6. Line 30 is dropping all packets not explicitly permitted, including BGP packets. The ACL needs to be modified to permit TCP port 179 packets.

<b>
R7# configure terminal

</b>

The BGP best path algorithm decides which is the best path to install in the IP routing table and to use for traffic forwarding. BGP assigns the first valid path as the current best path.


Enter the following configuration on the R6 router:
<b>
R6# configure terminal 
R6(config)# router bgp 65006
R6(config-router)# no neighbor 192.168.67.7 route-map MED in
R6(config-router)# neighbor 192.168.56.5 route-map MED in
R6(config-router)# end
R6# clear ip bgp * soft in

<h3>Monitor BGP</h3> 

<b>
R2# show ip bgp summary
</b>

This command is very useful when you are troubleshooting BGP. The output in the figure provides a short summary of the status of the BGP process in the router.

The first section of the output describes the BGP table and its content:

The BGP table version is the version number of the local BGP table. This number is increased every time that the table is changed.

The main routing table version shows the last version of the BGP database that was injected into the main routing table.

The subsequent lines of text indicate the amount of memory that has been allocated to hold the table. These lines of text display how many networks are known and how many different paths and attribute values are associated with them.

The second section of the output is a table in which the current neighbor statuses are shown. There is one line of text for each neighbor that has been configured. The columns are as follows:

IP address of the neighbor as configured in the local router

BGP version number that the router uses when communicating with the neighbor

AS number of the remote neighbor

Number of messages and updates that have been received from the neighbor since the session was established

Number of messages and updates that have been sent to the neighbor since the session was established

Version number of the local BGP table that has been included in the most recent update to the neighbor

Number of messages that are waiting to be processed in the incoming queue from this neighbor

Number of messages that are waiting in the outgoing queue for transmission to the neighbor

How long the neighbor has been in the current state and the name of the current state (the state "established" is not printed, so no state name indicates "established")


You can use this information to verify that BGP sessions are up and established. If they are not, you will have to further investigate the BGP configuration to locate the problem. You can also verify the IP address and AS number of the configured BGP neighbor


If the session state is established, the number of messages that have been sent and received, as displayed in the output of the <b>show ip bgp summary</b> command, can indicate BGP stability. Use the command a few times, with a time interval between the printouts, and calculate how many messages have been exchanged during that period.

Many messages in the incoming queue indicate a lack of CPU resources in the local router. Many messages in the outgoing queue indicate a lack of bandwidth to the remote router or a lack of CPU resources in the remote router.

To display information about the TCP and BGP connections to neighbors, use the show ip bgp neighbors EXEC command.

<h4> Monitor BGP Neighbors</h4>
<b>
R2# show ip bgp neighbors 172.16.12.11
</b>


Displays detailed neighbor information

You can use this command for two different purposes. The general purpose, as shown in the figure, is to get information about the TCP session and the BGP parameters of the session. All BGP session parameters are displayed. In addition, TCP timers and counters are also displayed.

The other use is not shown in this example. If any of the optional qualifiers referring to routes or paths are given, the BGP routing information that was sent or received on this session is displayed. This feature is useful when you are troubleshooting path selection.



To display entries in the BGP routing table, use the <b>show ip bgp</b> EXEC command.

R2# show ip bgp


Displays all routes in the BGP table in summary format

Usually, when the <b>show ip bgp</b> command is given without optional qualifiers, the entire BGP table is displayed. An abbreviated list of information about each route is displayed, one line per prefix. The output is sorted by the network number order. Therefore, if the BGP table contains more than one route to the same network, the routes are displayed on successive lines. The network number is printed on the first of these lines only. The following lines, which refer to the same network, have the network number field blank.

Some, but not all, of the BGP attributes that are associated with the route are displayed on the line. The next-hop, Multi-Exit Discriminator (MED) (displayed as Metric), local preference, and weight attributes each have their own columns. The AS-path attribute is displayed as the sequence of AS numbers in the Path column. Immediately following the AS path, but not part of the AS-path attribute, the origin attribute is displayed. The lowercase letter i means Interior Gateway Protocol (IGP), e means Exterior Gateway Protocol (EGP), and? means incomplete or unknown.

The BGP path selection process selects one of the available routes to each of the networks as the best. These routes are pointed out by the character > in the left column.

<b>
R2# show ip bgp 1.0.0.1
</b>

Displays detailed information about all paths for a single prefix

If more information and the complete set of BGP attributes are required, the show ip bgp command should be entered with the network number on the command line. This command displays all relevant BGP information about that specific network.


The BGP route selection process has selected this route as the best. So BGP will try to install this route into the routing table. The installation of routes in the routing table is made based on the administrative distance.


<h4>Troubleshoot BGP Neighbor Relationships</h4>


You may experience several common session startup issues when configuring basic BGP.

BGP Session Startup Problems—Common BGP Session Startup Symptoms:

BGP neighbors do not become active.

BGP neighbor is active, but the session is never established.

BGP neighbor status changes between idle and active.


BGP sessions to a router in another AS should normally run across directly connected interfaces (routers that share a common IP subnet). You must configure neighboring routers to reach each other by using the IP address belonging to this shared subnet so that no other routing protocol is required to set up the BGP session.

If a router is configured with a BGP neighbor that is in another Autonomous Sysetem (AS) but not directly connected, the session will stay in the idle state. The router will not even attempt to set up the session.

Symptom

· BGP neighbors do not become active.
. show ip bgp neighbors displays idle state.

Diagnosis

. The neighbor is not directly connected.

Verification

. Verify with show ip route.
. Directly connected external neighbor?
· EBGP Multihop?

The normal way to fix this problem is to change the neighbor reference so that it is referred by an IP address that is directly connected. However, in some odd cases, the neighbor is intentionally reachable by using an interface that is not directly connected. In that rare case, the local router must have routing information on how to reach that address. Also, you must configure the BGP session with the ebgp-multihop option.

If the session goes into the active state, the router will attempt to establish the session. If session establishment is unsuccessful, you will have to troubleshoot the problem. The <b>debug ip tcp transactions</b> command will display the connect attempts

Symptom

. The BGP neighbor is active; the session is not
established.
. debug ip tcp transactions: TCP SYN packet is
not answered with a SYN-ACK packet.

Diagnosis

. The neighbor is not reachable.

Verification

. Verify connectivity with ping.
. Check for the presence of an ACL.

TCP session establishment starts with the router sending a TCP SYN packet. If the TCP SYN packet is never answered, the remote router might be dead or not reachable. Try to use the ping command and verify the existence of the remote router and the IP packet exchange between the local and remote routers.



<h4>BGP Neighbor Not Reachable Example</h4>


In this example, the remote BGP router is not available.
<b>
ISP1# debug ip tcp transactions
Feb  6 05:04:01: TCP: sending SYN, seq 2161553223, ack 0
*Feb  6 05:04:31: TCB 0xEFE6AF18 destroyed
</b>

SYN packet is sent.

SYN-ACK reply never comes back. TCP session is closed.

The sending router never receives the reply to the SYN packet. The sending router aborts the TCP session in approximately 45 seconds (changing the state from SYN-SENT to closed).


If the TCP SYN packet is answered with a TCP RST packet, the remote router is alive and reachable but is not willing to grant the connection attempt. The reason for this refusal may be that BGP has not been fully configured on the remote router or the source IP address that is used by the local router in the connection attempt is not within the list of valid neighbors for the remote router.

Symptom

. The BGP neighbor is active, the session is not established.
. debug ip tcp transactions: TCP SYN packet is answered with an RST packet.

Diagnosis

. This router is not configured as the BGP neighbor.

Verification

. Check IP addresses of BGP neighbors with show ip bgp summary on the neighboring router.

ISP2# debug ip tcp transactions
*Feb  9 00:35:12: TCP: sending SYN, seq 4270019552, ack 0
*Feb  9 00:35:12: TCP0: connection closed - remote sent RST
</b>
SYN packet is sent.

Neighbor replies with an RST packet. TCP session is closed.

The remote router responds with an RST packet when it receives the initial SYN packet, terminating the BGP session.

If the TCP session is established by using the specified three-way handshake of SYN, SYN-ACK, and ACK, but the router drops the session after a short packet exchange, the BGP parameters are mismatched. Make sure that the remote AS that is configured on the router matches the local AS that is configured on the neighbor. If the AS numbers do not match, the router drops the session after exchanging BGP open messages.

<h3>Troubleshooting IBGP</h3>

There are several approaches for troubleshooting IBGP session startup problems.

Symptom

. The IBGP session does not start.

Diagnosis

. The IBGP session is run between loopbacks, and the update-source keyword is missing.

Verification

. debug ip tcp transactions: You should see BGP sessions coming from unexpected IP addresses.

When you configure IBGP sessions, a common mistake is to forget the <b>neighbor update-source</b> configuration command.

When you configure IBGP neighbors on the router, it is easy to remember to make a correct reference to the loopback interface of the remote router. But it is equally important to make sure that the correct source IP address of the outgoing TCP session is set. The peer router will not accept the session if the incoming source address does not match the peer router list of IBGP neighbors.

To verify that this issue is causing the problem, use the <b>debug ip tcp transactions</b>T command. The output of this command should display TCP SYN packets coming from unexpected IP addresses on the receiving router and TCP sessions being reset with TCP RST packets on the sending (misconfigured) router.

Symptom

. The IBGP session does not start.

Diagnosis

. Loopback interfaces are not reachable.

Verification

. Do an extended ping between loopback addresses to verify reachability.


An IBGP session between two routers can be established from the loopback interface of one router to the loopback interface of the other router only if the two routers can exchange IP packets that use those addresses as the source and destination. This exchange is possible only if the IGP carries the subnets that are assigned to each of the loopback interfaces.

When you verify reachability with the <b>ping</b> command, make sure that the ping packets are sourced from the loopback interface. Use an extended ping and explicitly refer to the IP address of the loopback interface to ensure that packets are sourced from the loopback interface.

Symptom

. The IBGP session does not start.

Diagnosis

. Packet filters prevent the establishment of BGP sessions.

Verification

. Debug ip tcp transactions for initial TCP SYN packets being rejected.

Packet filters can stop the BGP sessions. The path between the two BGP peer routers must be free from filters that block the BGP traffic.

BGP runs on the well-known TCP port 179. Both routers will make connection attempts to that destination port. They will use a high-numbered TCP port as the source. It is enough that one of the connection attempts succeeds. But for better performance during recovery from network failure, both attempts should have the possibility of succeeding. If both attempts do succeed, one of the connections will be brought down.

A router can use a BGP update to reach network destinations only if the next-hop address that is specified in the BGP update is reachable. A BGP update that refers to a next hop that is currently not reachable according to the routing table will be saved in the BGP table. However, the router cannot install this update in its routing table. If the next-hop address later becomes reachable, the BGP route will become a candidate route that the router could use for packet forwarding to that destination

Symptom

. An IBGP route is in the BGP table but is never selected as the best route.

Diagnosis

. The BGP next hop is not reachable.

Verification

. Use show ip bgp prefix to find the BGP next hop.
. Use show ip route to verify next-hop reachability.


To verify the next-hop reachability, check the BGP route in the BGP table by using the <b>show ip bgp prefix command</b>. The next hop is referred to as "inaccessible" if it is not currently reachable according to the routing table.

The next hop that is received in an incoming BGP update will be the far end of the EBGP session. If all routers in the local AS do not have a path to that subnet, the next-hop address will be inaccessible.

You can prevent this problem by including the subnet that links the transit AS to neighboring autonomous systems in the IGP. To perform this action, use either the <b>redistribute connected</b> command or the <b>network</b> and <b>passive-interface</b> configuration commands.

In old BGP designs, redistribution between BGP and an IGP was a common practice, and these protocols had to be synchronized to ensure proper packet forwarding. In modern designs, redistribution is no longer used and synchronization has to be turned off. The default value is disabled synchronization.

Symptom

. An IBGP route is selected as the best route but is not entered into the IP routing table.

Diagnosis

. BGP synchronization is not disabled.

Verification

. Disable BGP synchronization, clear the BGP sessions, and reexamine the IP routing table after the BGP table stabilizes.


Routers with BGP synchronization enabled will not be able to install IBGP routes in the routing table or propagate them to other EBGP neighbors.

You can fix this problem by configuring <b>no synchronization</b> in the router BGP configuration.


<h3>roubleshoot MP-BGP</h3> 


<b>Router# clear bgp ipv6 unicast *
Reset all IPv6 BGP sessions on the router.

Router# show bgp ipv6 unicast
Check the IPv6 BGP table.

Router# show bgp ipv6 unicast summary
Display the status of all IPv6 BGP connections.

Router# debug bgp ipv6 unicast updates
Display debugging messages for IPv6 BGP update packets.
</b>

MP-BGP extensions for IPv6 support the same features and functionality as IPv4 BGP. IPv6 enhancements to MP-BGP include support for an IPv6 address family and Network Layer Reachability Information (NLRI) and next hop (the next router in the path to the destination) attributes that use IPv6 addresses.

To configure IPv6-specific tasks, the IPv6 address family was introduced in the router configuration mode. Use the <b>address-family ipv6</b> command to enter the unicast IPv6 address family and <b>exit</b> to exit address family configuration. To configure IPv4-specific tasks, use the <b>address-familily ipv4</b> command to enter the unicast IPv4 address family.


There are two different ways to exchange IPv6 routes with BGP. You can exchange them over IPv4 TCP sessions or IPv6 TCP sessions. By default, neighbors that are defined using the <b>neighbor remote-as</b> command in router configuration mode exchange only IPv4 unicast address prefixes. To exchange IPv6 prefixes, neighbors must also be activated using the <b>neighbor activate</b> command in address family configuration mode for IPv6 prefixes.

When configuring IPv6 multiprotocol BGP between two IPv6 routers (peers) using link-local addresses, the interface for the neighbor is identified. This configuration is done using the <b>update-source</b> command. Also a neighbor may be configured using an IPv6 global next hop.

If peering is not established by this task, verify that a <b>route-map set ipv6 next-hop</b> command has been configured. Use the debug bgp ipv6 unicast update command to display debugging information on the updates to help determine the state of the peering. When forming IPv6 TCP sessions and neighbor relationships, you do not have to worry about the issue just described. However, you have to make sure that you define the IPv6 neighbor and activate it.

To inject a network into IPv6 BGP database, you must define the <b>network</b> using the network command in address family configuration mode for the IPv6 BGP database.


By default, route maps that are applied in router configuration mode using the <b>neighbor route-map</b> command are applied to only IPv4 unicast address prefixes. Route maps for the IPv6 address family must be applied in address family configuration mode using the <b>neighbor route-map</b> command. The route maps are applied either as the inbound or outbound routing policy for neighbors under the IPv6 address family.

Redistribution is the process of redistributing, or injecting, prefixes from one routing protocol into another routing protocol. Prefixes that are redistributed into IPv6 multiprotocol BGP using the <b>redistribute</b> router configuration command are injected into the IPv6 unicast database.

Symptom

. A BGP IPv6 route is in the BGP table but is never selected as the best route.

Diagnosis

. The BGP next hop is unreachable because it is an IPv4-mapped IPv6 address.

Verification

. Use show bgp ipv6 unicast to verify next hop.
. Use a route map to change the default next hop address to the advertising interface's IPv6 address.

A common issue when configuring MP-BGP for IPv6 over an IPv4 connection is the incorrect next hop being advertised between BGP neighbors.

First, verify that the IPv6 BGP neighbor session is established using the <b>show bgp ipv6 unicast summary</b> command, as show in the figure.


verify the IPv6 BGP table. Notice in the figure that the next hop being learned by R1 for the 2001:DB8:2::/64 network is an invalid IPv4-mapped IPv6 address of ::FFFF:2.2.2.2. Because this next hop is unreachable, the route to the 2001:DB8:2::/64 network is not chosen by BGP as the best entry for that network.

<b>
R2#config t
R2 (config) #route-map NEXT-HOP permit 10
R2 (config-route-map) #set ipv6 next-hop 2001:db8 : 12: :2
R2 (config-route-map) #exit
R2 (config) #router bgp 65502
R2 (config-router) #address-family ipv6 unicast
R2 (config-router-af) #neighbor 1.1.1.1 route-map NEXT-HOP out
</b>

The solution is to create a policy that changes the default next hop address to the advertising interface’s IPv6 address. The figure shows the creation of a route map named NEXT-HOP, which has no explicit match statement so will apply to all prefix being advertised from R2 to R1. The route map changes the next-hop address of all routes to 2001:DB8:12::2, the IPv6 address of R2’s interface to R1. The route map is then applied as an outgoing policy to the neighbor statement under the BGP IPv6 address family configuration. It is applied only here and not to the default IPv4 address family configuration, as the route map has no relevance to the IPv4 prefixes R2 could possibly be advertising to R1.

One possible solution to avoid this issue entirely, is to use separate IPv4 and IPv6 BGP sessions for the IPv4 and IPv6 routes to be advertised. In the figure, R1 is now configured with an IPv6 neighbor (2001:DB8:12::2). The router is now running a dual-session configuration. This is used in practice far more commonly than either the IPv4-only session demonstrated previously. They are simpler and allow more separation of control between IPv4 and IPv6. The only potential drawback is that they double the number of BGP sessions maintained by the router. Usually this does not matter, but in a case in which a router connects to large numbers of neighbors, this doubling could present a scaling problem.

In summary, some useful commands to troubleshoot IPv6 BGP are listed here:
<b>
clear bgp {ipv4 | ipv6} — Use the unicast * command to reset all BGP sessions on the router. You can use several other keywords such as, the IP address of the neighbor, the AS number, and so on, instead of the asterisk to make some more specific clearing.

show bgp {ipv4 | ipv6} — Use the unicast command to display the BGP table. You can see the prefixes with the next-hop address, local preference, metric, AS path, and so on.

show bgp {ipv4 | ipv6} — Use the unicast summary command to verify all BGP connections.

debug bgp {ipv4 | ipv6} — Use the unicast updates command to enable debugging for all update packets that are received and sent by the router.
</b>
