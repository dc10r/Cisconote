<h3>Troubleshoot AAA Issues</h3>


A junior administrator reconfigured access restriction on BR. They want to use a username-password combination of "admin/cisco" and use these credentials as the local AAA database for login. However, when trying to use Telnet to connect from CORE to BR, BR is still asking just for the password.


On router CORE, verify the problem by using Telnet to connect to router BR.


<b>
CORE# telnet 10.3.0.2
</b>

To verify if the problem exists, use Telnet to connect to router BR. As you can see from the output, only the password is required to access router BR. You can conclude that the problem exists, and you should start troubleshooting.

You were told by the junior administrator that they had reconfigured access restrictions on router BR. They want the username/password combination to be used for authentication when accessing router BR. But the configuration is not correct because only the password is required.

Using a “top-down” approach to troubleshooting a faulty access policy, first check the VTY line configuration on router BR.

On router BR, check the VTY line configuration.

<b>
BR# show running-config | section line vty
line vty 0 4 
 privilege level 15
 password cisco
 login
 transport input telnet ssh
</b>


First, use the current Telnet connection to router BR from router CORE and check the VTY line configuration on the BR router. As you can see, the basic login command is used for authentication to the router. This configuration means that the router will authenticate the access by checking the password that is configured with the password command under the VTY line.

On router BR, check if AAA is configured.

<b>
BR# show running-config | section aaa
no aaa new-model
</b>
As you can see, AAA is not configured. You can conclude that this configuration is part of the issue. According to the ticket, AAA needs to be configured on router BR.
On router BR, verify if any username and password are configured.

<b>
BR# show running-config | section username
username admin privilege 15 password 0 cisco
</b>

When configuring AAA services with the aaa new-model command, local authentication is immediately applied to all lines except the console line. If a new Telnet or SSH session is opened to the router after enabling this command, the user has to be authenticated by using the local database of the router. Therefore, you should check if any user is configured; otherwise, you will not be able to access the router. As you can see, the admin user exists.


On router BR, enable AAA and configure local authentication.
<b>
BR(config)# aaa new-model 
BR(config)# aaa authentication login default local
</b>
You can enable AAA services and configure the local authentication with the aaa authentication login default local command. With this command, the local database will be used for authentication by default. After AAA services have been configured, you can initiate a new Telnet session to check if the configuration has been correctly assigned.

On router BR, exit the current Telnet session. Once back at the CORE router prompt, initiate a new Telnet session to the BR router. The local database should be used for authentication.

<b>
BR(config)# exit
BR# exit

[Connection to 10.3.0.2 closed by foreign host]
CORE#
CORE# telnet 10.3.0.2
Trying 10.3.0.2 ... Open

User Access Verification

Username: admin
Password: (cisco)

</b>

After enabling AAA services, you should test access to router BR. Use telnet 10.3.0.2 to access router BR from CORE. As you can see from the output, router BR now asks for a username and password. After providing the correct credentials, you are connected to router BR.

Ideally, you would leave the current session to BR open and initiate another one from a different device. This would lessen the risk of locking yourself out of the device in case you misconfigured remote access.

You can conclude that the issue is solved. Exit the Telnet session to return to the CORE router prompt.

<h4>Troubleshoot Cisco IP SLA Tracking Issues</h4> 

After a recent outage on ISP1, a junior administrator was tasked with testing the current IP SLA configuration on EDGE to ensure that when connectivity is lost to the 209.165.200.129 address hosted on ISP1, the secondary link to ISP2 is used for Internet access. After performing the requested testing, they are reporting that EDGE is not failing over to ISP2 as required. You need to troubleshoot and correct this issue

On router EDGE, start by testing the current routing configuration. Ping the ISP1-hosted address used for SLA testing (209.165.200.129) and an Internet-based IP address (209.165.201.129).


<b>

EDGE# ping 209.165.200.129
success
EDGE# ping 209.165.201.129
success

</b>
The EDGE router is successfully routing packets via ISP1. Investigate the default route that is configured on EDGE.


On router EDGE, verify the routing table for a default route to ISP1.


<b>
EDGE# show ip route static | include 0.0.0.0
</b>

EDGE has a default route that points to the next hop 209.165.201.6 which is on ISP1. The junior administrator informed you when connectivity is lost to 209.165.200.129, the secondary link to ISP2 is not operational. To verify the problem, you need to disable the loopback 0 interface on router ISP1 to simulate a failure.


On router ISP1, disable the loopback 0 interface to simulate a failure.

<b>
ISP1(config)# interface Loopback 0
ISP1(config-if)# shutdown
</b>

With the ISP1 loopback 0 interface shutdown, the path to ISP2 should become active and access to the Internet should still be available. Ping the Internet-hosted address 209.165.201.129.


On router EDGE, ping the Internet-hosted address 209.165.201.129.


<b>
EDGE# ping 209.165.201.129
unsuccessfull
</b>

The issue is confirmed. Failover through ISP2 is not occurring and the ping displays U.U.U since the destination is unreachable. You can start troubleshooting.

According to the network requirements, an IP SLA is configured to test the reachability of 209.165.200.129. Start by investigating the IP SLA configuration.


On router EDGE, verify the IP SLA configuration.

<b>
EDGE# show running-config | section ip sla

The IP SLA configuration appears correct. It is sending an ICMP Echo Request every five seconds to address 209.165.200.129. The IP SLA schedule is also correct.

With the ISP1 loopback 0 interface disabled, it is expected that the SLA would be reporting a timeout and lack of connectivity. You can verify this with the <b>show ip sla statistics</b> command:

EDGE# show ip sla statistics    
</b>
The failures will continue to increment while the ISP1 loopback 0 interface is disabled.

Since the requirement is for the IP SLA to be used to track reachability of the 209.165.200.129 address, verify if a tracking object has been configured and applied to the default route.


On router EDGE, use the show track command and the <b>show running-configuration | include ip route 0.0.0.0</b> command.

<b>
EDGE# show track
EDGE#
EDGE# show running-config | include ip route 0.0.0.0
</b>


The output confirms the following issues:

No tracking object is configured on the router.

The default route to ISP1 is not configured with the tracking option.

There is no default route to ISP2 to be used if there is IP SLA failure.

You need to resolve all these issues to fix the problem reported by the junior administrator.

Start by defining a tracking object that will use the IP SLA.


On router EDGE, create a tracking object that will verify the reachability status of the IP SLA. Use the number 10 for the tracking object and track the reachability of IP SLA 1. Configure a tracking delay of 2 seconds when the IP SLA state goes from up to down, and a delay of 5 seconds when the IP SLA state goes from down to up.

<b>
EDGE(config)# track 10 ip sla 1 reachability
EDGE(config-track)# delay down 2 up 5
</b>

Use the track command to create a tracking object that verifies the reachability of IP SLA 1. Configure the delay command to specify a period to wait before communicating state changes of a tracked object.

On router ISP1, enable the loopback 0 interface.

<b>
ISP1(config)# interface Loopback 0
ISP1(config-if)# no shutdown
</b>

With the loopback 0 interface now enabled, return to the EDGE router and investigate the console message that has appeared.


On router EDGE, investigate the console message and verify the status of the IP SLA and the tracking object using the <b>show ip sla statistics</b> and the <b>show track</b> commands.

<b>
EDGE#

EDGE#

EDGE# show ip sla statistics

EDGE# show track

    2 changes, last change 00:12:14

First, a Syslog message appears at the console indicating that the state of the tracking object has gone from down to up, since the IP SLA is now able to reach the 209.165.200.129 address.

Second, the IP SLA is returning an OK operational code to the tracking object since reachability is up.

The next step in fixing the failover issue is by adding the tracking option to the current default route. This will allow the router to remove that route from the routing table if the tracking object goes down.

On router EDGE, remove the original default route and configure an identical one but add the tracking option to the default route using tracking object 10.

<b>
EDGE(config)# no ip route 0.0.0.0 0.0.0.0 209.165.201.6
EDGE(config)# ip route 0.0.0.0 0.0.0.0 209.165.201.6 track 10
</b>
It is necessary to remove the old default route before adding the new route with the tracking option, or else the router will keep both static routes in its running configuration.


The final step in fixing the issue is by configuring a second default route. This one will point to ISP2 but will have a higher administrative distance so that the original default route to ISP1 takes precedence when the IP SLA is able to reach the 209.165.200.129 address. The second default route with a higher administrative distance is often referred to as a floating static route. A floating static route floats or moves into and out of the IP routing table depending on whether the better (lower) administrative distance route happens to exist currently. Basically, the router ignores the static route during times when the better route is available.


On router EDGE, configure a second default route that points to 209.165.200.6 (ISP2) but with an administrative distance of 2.

<b>
EDGE(config)# ip route 0.0.0.0 0.0.0.0 209.165.200.6 2
</b>

The backup default route to ISP2 will “float” above the original route to ISP1 that has a default administrative distance of 1. If the tracking object goes down, EDGE will remove the route to ISP1 and install the route to ISP2 instead.


Before testing the failover process, inspect the status of the routing table on EDGE and the configured default routes in the running configuration.

On router EDGE, use the <b>show ip route 0.0.0.0<b> and the <b>show running-config | include ip route 0.0.0.0</b> commands.


<b>
EDGE# show ip route 0.0.0.0
EDGE# show running-config | include ip route 0.0.0.0
</b>
The EDGE router is currently using the default route to ISP1 with an administrative distance of 1 but notice that both default routes are in the running configuration: one with the tracking option and the other with the higher administrative distance.


You are now ready to test the failover between ISP1 and ISP2. You will start by tracing the path to the public Internet-hosted 209.165.201.129 address to confirm that EDGE is currently using the path to ISP1. You will then disable the loopback 0 interface on ISP1. When the tracking object goes down, you will repeat the same trace and inspect the routing table on EDGE.

On router EDGE, use the traceroute command to verify the path taken to reach 209.165.201.129.


<b>
EDGE# traceroute 209.165.201.129
</b>
The EDGE router takes the path through ISP1 to reach 209.165.201.129 address since the tracking object is reporting that the IP SLA is able to reach the 209.165.200.129 address on ISP1.

On router ISP1, disable the loopback 0 interface.

<b>
ISP1(config)# interface Loopback 0
ISP1(config-if)# shutdown
</b>


Wait a few moments, and then inspect the Syslog message that appears on the EDGE router:

<h3>AAA Overview</h3>


Recall that AAA stands for authentication, authorization, and accounting. Authentication is about determining identity. Authorization is about defining what individual or groups of identities can do. Accounting is about keeping track of what individual identities have done. AAA can be associated with network access (for example via VPN) and with administrative access for device management.

Authentication: Who are you?

Authorization: What can you do? What can you access?

Accounting: What did you do? How long did you do it? How often did you do it?


Administrative access: Console, Telnet, and auxiliary access

Remote user network access: VPN access

AAA data must be stored somewhere. The simplest implementation is to use the local database on individual network devices. This means AAA authentication and authorization data are stored directly in the device’s configuration. While simple, using the local AAA database does not scale well. In all but the smallest deployments, centralized AAA is preferred over local AAA. 

With centralized AAA, configuration and maintenance of AAA policy is much simpler. User IDs are defined and managed centrally and made available all devices in the network. Centralized servers can provide an authoritative source for AAA policy to all network devices. Generally, the user repository is stored outside of the AAA servers, commonly in Active Directory or Lightweight Directory Access Protocol (LDAP). The AAA servers will consult one of these servers during the authentication process, but authorization and accounting are generally handled by the AAA servers themselves.

Local authentication:

User establishes connection with the router.

Router prompts user for username and password, authenticating the user using a local database.

Server-based authentication:

User establishes connection with the router.

Router prompts user for username and password.

Router passess username and password to AAA server (Cisco ISE).

The server authenticates the user.


For centralized AAA, there are two AAA protocols that are commonly implemented in today’s IP-based networks. They are RADIUS and TACACS+. Cisco offers a AAA solution for the enterprise market that now supports both protocols: Cisco ISE v2.0 (Identity Services Engine). Cisco ISE is a next-generation identity management system that adds features such as profiling, posture assessment, and centralized web authentication.

<h3>Configuration Using Local Database</h3>


The following configuration enables AAA and specifies that the local database will be used for user authentication and EXEC access authorization decisions, and adds one username to the local database:

<b>
Router(config)# aaa new-model
Router(config)# aaa authentication login default local
Router(config)# aaa authorization exec default local
Router(config)# username adminsr privilege 15 secret srPass
Router(config)# enable secret secretPass
</b>
The aaa new-model command enables AAA features, and the aaa authentication, aaa authorization, and aaa accounting commands define those features. Consider the following command:
<b>
aaa authentication login {default | list-name} method1 [method2 ...]
</b>


This command specifies a list of authentication methods. The simplest configuration will use the keyword default and specify local as the single method. The default method list is used on all lines (VTY, CON, and AUX), unless a specific named method list is explicitly defined for a line. Also consider the next command:

<b>
aaa authorization exec {default | list-name} method1 [method2 ...]
</b>

This command specifies how to determine whether an authenticated user is authorized to connect to the device’s EXEC process (the command shell). Again, the simplest configuration will use the keyword default and specify local as the single method.

Entries in the local database are configured with the username command.

<b>
username name [privilege level] [secret {0| 5| password}]
</b>

There are several other options available with the username command, but in general it is used to define a user ID, the privilege level of that user, and the password that is assigned to the user ID. Both the keyword password and the keyword secret are available. The secret will be stored in the configuration in a more secure fashion than the password. Passwords can be encrypted with a weak encryption algorithm using the service password-encryption command, whereas secrets are stored as much stronger salted MD5 transforms.

In the configuration example, the first command enables AAA. Until the aaa new-model command is entered, the AAA authentication, authorization, and accounting commands are not available. After aaa new-model, the next two commands state that, by default, the VTY lines will use the local database for user authentication and EXEC access authorization decisions. The command defines a username with a privilege level and a password. (The password that is used in the example is not considered strong. In a production environment, care should be taken to ensure that passwords are much more difficult to crack than the password in the example.) If user admins connects to a VTY line via SSH and successfully authenticates, user admins will automatically be assigned privilege level 15.

Line CON 0 is treated differently than the VTY lines. If authorization is misconfigured, it is possible for administrators to lose configuration privileges and hence the ability to correct the misconfiguration. To prevent this situation, authorization is not implemented on line CON 0 by default, so it can be used as a fallback method to fix the configuration. The last line of the configuration above is needed for this fallback method to work. An administrator can use the enable secret to reach privilege level 15 on line CON 0 when necessary. A riskier option would be to use the command aaa authorization console, which would then enforce AAA authorization on line CON 0.

<h3>AA Configuration Using a AAA Server</h3>


Using the local database with privilege levels can be effective in smaller environments, but neither technique scales well. If there are hundreds or thousands of network devices, it is very difficult to configure and maintain user IDs and authorization definitions across all the devices. Using centralized AAA servers is much more scalable.

This topic will focus on configuring IOS devices to utilize a TACACS+ server for authentication, authorization, and accounting.

The first thing to do when configuring TACACS+ on an IOS device is to define the TACACS+ servers. At a minimum, the device needs to know the IP address of the server and the pre-shared key that is used to protect traffic between the device and the server. This configuration is done by using the tacacs server command and specifying the address and key in the TACACS+ server configuration mode.

The following configuration enables AAA and specifies that the TACACS+ server at 172.16.10.10 will be used for user authentication and EXEC access authorization decisions, and adds one username to the local database for fallback:

Router(config-server-tacacs)# address ipv4 172.16.10.10
Router(config-server-tacacs)# key SecretKeyString
Router(config-server-tacacs)# exit
Router(config)#

You will still utilize the commands aaa new-model, aaa authentication login, and aaa authorization exec. The difference is the method list will now include group tacacs+. Because connectivity to the TACACS+ server may fail, it also makes sense to define two methods in the list: group tacacs+ and local. If the TACACS+ server request fails, the local database can be used as a fallback.

If the administrator is authorized for the command, the command will be executed normally. If the administrator lacks authorization, the command has no effect and an error message is displayed.

A TACACS+ server is also capable of keeping accounting records of administrative access sessions and of individual commands. This command will cause an accounting record to be sent at the start of an administrative access session to the device’s EXEC process, and another accounting record to be sent at the end of the session.

The accounting commands in the example will cause an accounting record to be sent for every privilege level 15 command and every configuration mode command that is entered by the user.

The accounting records are very detailed and include data such as the device identity, the user identity, the IP address from which the user is connected, and the date and time stamps that are associated with the activity.

<h3>Troubleshoot AAA</h3>


AAA services are used to control access to the management plane of the router or switch. You can use the local user database or a database on a remote server with the protocols such as TACACS+ or RADIUS. TACACS+ is a Cisco proprietary protocol that works over TCP port 49, while RADIUS is the Internet Engineering Task Force (IETF) standard that uses UDP port 1812 (or 1645) for authentication and UDP port 1813 (or 1646) for accounting.

It is the best practice to use a centralized AAA server with a local method as a backup in cases when the AAA server is not accessible.

After AAA is enabled, you can configure authentication, authorization, and accounting methods. AAA services use the concept of a named list, which could be used under a different location to where AAA services are used. You can also use the default list, which means that this list is used when no other list is specified.


Some common TACACS+ failures can include the following:

The TACACS+ server is not accessible.

A mismatch between shared keys occurs.

The user credentials are rejected by the server.

Common RADIUS problems are similar to TACACS+ problems:

A RADIUS server failure or loss of network connectivity happens.

A mismatch of the shared key between the RADIUS server and client happens.

The user credentials are wrong.

A mismatch between the RADIUS ports on the RADIUS server occurs.

Some of the common problems of TACACS+ and RADIUS servers are similar:

The server fails, or the server is not accessible: To prevent locking yourself out of the device when the AAA server is not accessible, use the local method as a backup for authentication. You can define up to four methods for authentication.

A mismatch between shared keys occurs: Both protocols need a shared key to be used for authenticating a network device. If the keys do not match on the remote server and network device, the network device will not be able to access the user database.

The user credentials are rejected by the server: Usually, you can check in server logs to verify if a user was correctly authenticated or authorized. When users are rejected, you should check these logs to verify if the provided credentials were correct.

In addition to these common problems, there could be RADIUS ports that mismatch. Cisco uses UDP port 1645 and 1646 by default. UDP ports 1812 and 1813 are ports that are specified in the standard. Usually, servers listen on both sets of ports for backward compatibility, but you should always check if the correct ports are used.

</b>

Check the running-config for AAA configuration.

<b>

</b>

Debug authentication on the router.

<h3>SNMP SIMPLE NETWORK MANAGEMENT PROTOCOL</h3>

SNMP has developed a bad reputation from a security perspective. The reputation was deserved with SNMP versions 1 and 2c which are both cleartext protocols and use the concept of community strings for authorization. Note that the original definition of SNMP version 2 introduced a different authorization methodology, but it was unpopular and not widely implemented. SNMP version 2c is SNMP version 2 using the SNMP version 1 concept of community strings.


Management Information Bases, or MIBs are a key component of SNMP.

Access is accomplished with get operations and set operations.

Unsolicited notifications via trap and inform operations.


All versions of SNMP utilize the concept of the Management Information Base (MIB). Access is accomplished with GET operations and SET operations. GET operations allow the management system to retrieve status and configuration data from the device. Set operations allow the management system to modify the configuration on the device. Both SNMP version 1 and 2c use the concept of community strings to authorize access to data stored in the MIB. A GET request will be honored with either a read-only or a read-write community string. A SET operation requires a read-write community string. Community strings are less secure than passwords because they are contained in every SNMP request. If an attacker can capture just one SNMP packet, they can obtain the cleartext community string.


SNMP also supports unsolicited notifications that are sent from devices to SNMP management systems. The original notification mechanism was called a trap. The management system is not expected to acknowledge a trap. SNMP version 2 introduced the inform mechanism. An inform is identical to a trap, but an acknowledgment is expected. Devices will queue and resend unacknowledged informs.

Configuring SNMPv2c is similar to configuring SNMPv1. The only difference is with SNMP trap or inform configuration. You can use the following commands to configure basic SNMPv2c operation:

<b>
Router(config)# access-list access-list-number permit ip-addr
Router(config)# snmp-server community string [ro | rw] [access-list-number]
Router(config)# snmp-server host host-address [traps] [informs] version 2c community- string [trap-type]
</b>

First, define a standard IP access list that permits only the IP address of your SNMP agent machine. Then apply that access list to the SNMP community string with the snmp-server community command. Use the ro keyword to allow read-only access by the SNMP manager; otherwise, you can use the rw keyword to allow both read and write access


Finally, use the snmp-server host command to identify the IP address of the SNMP manager where SNMP traps will be sent. By default, all types of traps are sent. You can use the ? key in place of trap-type to see a list of the available trap types.

In the snmp-server host command, use the version 2c keywords to identify SNMPv2c operation. By default, regular SNMP traps are sent. To use inform requests instead, add the informs keyword.


<h4>SNMPv2c Configuration</h4>


The following configuration allows SNMP polling from network management stations at 172.17.250.5 only. The community string MyString is used to authenticate the SNMP requests. All possible SNMP informs are sent to 172.17.250.250.


<b>
Router(config)# access-list 5 permit 172.17.250.5
Router(config)# snmp-server community MyString ro 5
Router(config)# snmp-server host 172.17.250.250 informs version 2c MyString
</b>

SNMP version 3 replaces community strings with a user-based security model, and its architecture provides origin authentication, data integrity, and privacy. Authentication and privacy security mechanisms are optional.


<h4>SNMPv3</h4>


SNMP version 3 replaces community strings with a user-based security model:

Origin authentication

Data Integrity

Privacy


SNMP version 3 can be configured in the following three modes:

noAuthNoPriv: No cryptographic hash or encryption

AuthNoPriv: Use of cryptographic hash to secure authentication credentials, but no encryption for data

AuthPriv: Use of cryptographic hash to secure authentication credentials and also encryption for data privacy


SNMPv3 uses the concept of engine IDs. Each system in the management domain requires a unique engine ID. The engine ID is composed of 24 hexadecimal characters. The device will append leading zeros to the engine ID if fewer characters are specified. One strategy for assigning engine IDs is to translate the decimal representation of the IP address of a device into a 12-digit string. If informs are to be used, remote engine IDs must be defined, corresponding to the network management station. The syntax for defining SNMPv3 engine IDs is as follows:

<b>
snmp-server engineID {local engine-id | remote ip-address [udp-port udp-port-number] [vrf vrf-name] engine-id-string}
</b>

Configuration of the user-based security model in SNMPv3 begins with the configuration of groups. The group will specify the cryptographic policy to be used by the group and optionally authorization for read and write access to the MIB can be specified with read views and write views. By default, a group is allowed read access to the entire MIB, and write access is not allowed.


SNMP groups and views are defined with the following commands:

<b>
snmp-server group [groupname {v1 | v2c | v3 [auth | noauth | priv]}] [read readview] [write writeview] [notify notifyview] [access access-list]
snmp-server view view-name oid-tree {included | excluded}
</b>

Once the groups are configured, SNMP users can be defined. The user is assigned to a group. The security services that are specified by the group are more specifically defined at the user. If authentication is configured, the authentication hash algorithm and the authentication shared secret for this user is defined with the user. If privacy is configured, the encryption algorithm and the privacy shared secret is defined with the user.

The syntax for the snmp-server user command is as follows:

<b>
snmp-server user username group-name [remote host [udp-port port] [vrf vrf-name]] {v1 | v2c | v3 [encrypted] [auth {md5 | sha} auth-password]} [access [ipv6 nacl] [priv {des | 3des | aes {128 | 192 |256} privpassword] {acl-number | acl-name}]
</b>

<h4> SNMPv3 Configuration</h4>
An example configuration of SNMPv3 is as follows:

<b>
Router(config)# access-list 5 permit 10.10.10.0 0.0.0.255
Router(config)# snmp-server engineID local 010010010099
Router(config)# snmp-server view nms-view 1.3.6.1.2.1 included

In the example, a router is configured for SNMPv3 operation. Access list 5 permits only stations in the 10.10.10.0/24 subnet with SNMP access. SNMPv3 access is defined for a group named nms-group using the priv (authentication and encryption) security level with write rights for a view called nms-view. One SNMPv3 user named nms-user is defined; the network management station will use that username when it polls the switch for information. The username will require SHA packet authentication and AES-128 encryption, using the auth-pass and priv-pass passwords, respectively. The defined view allows visibility into MIB-2 and Cisco MIB data.

Finally, SNMPv3 traps will be used to send alerts to station 10.10.10.50 using the priv security level and username nms-user.

<h3>Syslog</h3>

IOS administrators generally become familiar with seeing syslog messages on the router console. Some common syslog messages that you may have seen include:

%SYS-5-CONFIG_I: Configured from console by console
%LINK-3-UPDOWN: Interface FastEthernet0/0, changed state to down
Syslog was originally developed to provide monitoring and auditing of the UNIX Sendmail service. Other applications began to use the service, and it grew to be the standard logging solution on UNIX and UNIX-like operating systems. Syslog has been adopted by many network device manufacturers, and it was standardized in RFC 5424.

Generally, when an event occurs that is deemed important by a service, the service generates a syslog message to document the event. On Cisco IOS devices, by default, syslog messages are sent to the console, to the terminal monitor, and to a local buffer. Optimally, syslog messages should be sent to a centralized repository, where they can be aggregated and analyzed. A syslog server normally listens on UDP port 514. More recently, servers using TCP have been implemented, providing greater reliability in message delivery.

Facilitates monitoring and auditing

Messages generated for important events

Syslog messages sent to the console, the terminal monitor, and a local buffer

Syslog messages should be sent to a centralized repository

Syslog severity levels 0–7


Syslog defines eight severity levels: 0–7. The lower the number, the more severe the issue. Syslog also defines standard names that are associated with each level.

Within IOS, the severity levels that are associated with events are often more in line with device health and network management than they are with security. For example, the following four messages are listed in order of severity.


<h4>Syslog Messages</h4>


Syslog message fields:

Timestamp: The date and time from the internal clock.

Facility Code: A system identifier that categorizes the function or module that has generated the message; the facility code always begins with a percent sign.

Severity: A number from 0 to 7 that indicates how important or severe the event is; a lower severity means that the event is more critical.

Mnemonic: A short text string that categorizes the event within the facility code.


Obviously, a power supply failure (severity level 1) is an urgent issue, as it affects the operating health of a device and of the network in which it resides. An interface failure (severity level 3) is generally less severe than a complete device failure, but it can certainly affect the device and the network. A configuration change (severity level 5) is routine in network maintenance and is assigned a relatively low severity. But from a security perspective, auditing configuration changes is very important. The last example is a logged hit on an ACL. If a security administrator has specified the log option on a particular line in the ACL, this event is probably significant. However, the severity level is only a 6. It is important to note that the severity levels on syslog messages are not necessarily prioritized according to security.

While logging to the console is enabled by default, it is the most expensive regarding CPU resources on an IOS device. This is because the console is a character-by-character serial device. Each character that is displayed to the console requires a CPU interrupt. As such, it is common to disable logging to the console when logging to a centralized syslog server is configured. Access to a device’s CLI can be provided by physical connections to the console port or AUX port. This direct serial connection to the device can facilitate an out of band management access method. The CLI can also be reached via networking protocols via a device’s VTY lines. In the past, Telnet was commonly used as a protocol for accessing a network device’s CLI. While the use of Telnet does persist, its popularity is waning due to security concerns. Telnet does not provide any privacy. Not only is the data sent cleartext, authentication credentials are also sent cleartext. If an attacker can sniff a Telnet session, they can capture the administrator’s username and password. Because of this, SSH has become the standard for CLI access via the network. <h3>NetFlow</h3> 

NetFlow is a Cisco IOS application that provides statistics on packets flowing through the routing devices in the network. It is emerging as a primary network accounting and security technology. NetFlow identifies packet flows for both ingress and egress IP packets. NetFlow is completely transparent to the existing network, including end stations and application software and network devices like LAN switches. Also, NetFlow capture and export are performed independently on each internetworking device; NetFlow does not need to be operational on each router in the network.


NetFlow is a Cisco IOS application that provides statistics on packets flowing through the routing devices in the network.

Performs capture and export independently on each internetworking device

Need not be operational on each router in the network

Groups packets into flows and then tallies packets and bytes

Version 5: Popular NetFlow version, limited to IPv4 flows

Version 9: Template-based, used to report IPv4, IPv6, MPLS, BGP flows


A NetFlow network flow is defined as a unidirectional stream of packets between a given source and destination. The source and destination are each defined by a network-layer IP address and transport-layer source and destination port numbers.


Specifically, a flow is defined by the combination of the following seven key fields:

Source IP address

Destination IP address

Source port number

Destination port number

Layer 3 protocol type

ToS

Input logical interface

These seven key fields define a unique flow. If a packet has one key field different from another packet, it is considered to belong to another flow. A NetFlow report is often compared to a phone bill. A phone bill specifies the phone calls made by the source phone. It does not provide any data on the actual conversations that took place, but it does provide information such as the time of the call and the duration of the call.


Analyzing NetFlow data can’t reproduce the actual communication that took place in any individual connections, but it does provide information on which systems communicated with which other systems at which times over which protocols and ports. This data can be used to recognize unusual traffic patterns which may be indicative of a network attack. It can also be used for forensic analysis during and after an attack takes place.

<h3>Cisco Flexible NetFlow</h3> 

Original NetFlow uses a fixed seven tuples of IP information to identify a flow. Flexible NetFlow allows the flow to be user-defined. The benefits of Flexible NetFlow include:


High-capacity flow recognition, including scalability and aggregation of flow information.

Enhanced flow infrastructure for security monitoring and DDoS detection and identification.

New information from packets to adapt flow information to a particular service or operation in the network. The flow information available will be customizable by Flexible NetFlow users.

Extensive use of Cisco flexible and extensible NetFlow Version 9 and version 10 export formats. With version 10 export format, support for variable length field for the wireless client's SSID is available.

A comprehensive IP accounting feature that can be used to replace many accounting features, such as IP accounting, Border Gateway Protocol (BGP) Policy Accounting, and persistent caches.


Evolution from traditional NetFlow

Can collect and export network information and statistics

Export format can be v9 or IPFIX

Required to collect information from NBAR/NBAR2

Monitors layers 2–7

Who, what, when, where


Original NetFlow allows you to understand the activities in the network and thus to optimize network design and reduce operational costs. Flexible NetFlow allows you to understand network behavior with more efficiency, with specific flow information tailored for various services used in the network. The following are some example applications for a Flexible NetFlow feature:

Flexible NetFlow enhances Cisco NetFlow as a security monitoring tool. For instance, new flow keys can be defined for packet length or MAC address, allowing users to search for a specific type of attack in the network.

Flexible NetFlow allows you to quickly identify how much application traffic is being sent between hosts by specifically tracking TCP or UDP applications by the class of service (CoS) in the packets.

The accounting of traffic entering a Multiprotocol Label Switching (MPLS) or IP core network and its destination for each next hop per class of service. This capability allows the building of an edge-to-edge traffic matrix.


<h4>Cisco Flexible NetFlow Configuration</h4>

To configure Flexible NetFlow, follow these general steps:

Configuring Flexible NetFlow is a four-step process. First, a customized flow record is created. Customized flow records are used to analyze traffic data for a specific purpose.



A customized flow record must have at least one match criterion for use as the key field and typically has at least one collect criterion for use as a nonkey field. Second, a custom flow exporter is created. Each flow exporter supports only one destination. If you want to export the data to multiple destinations, you must configure multiple flow exporters and assign them to the flow monitor. 

Third, a customized flow monitor is created. Each flow monitor has a separate cache assigned to it. Each flow monitor requires a record to define the contents and layout of its cache entries. These record formats can be one of the predefined formats or a user-defined format. Finally, apply a flow to an interface in the input or output direction.


Step 1: Configure a Flow Record

<b>
R1(config)# flow record R1-FLOW-RECORD
R1(config-flow-record)# match ipv4 source address
R1(config-flow-record)# match ipv4 destination address
R1(config-flow-record)# match ipv4 protocol
R1(config-flow-record)# collect interface input
R1(config-flow-record)# collect counter bytes
</b>

In the configuration for step 1, a flow record named R1-FLOW-RECORD is defined that will track the IPv4 source and destination address, and the IPv4 protocol number. The flow record will also collect interface and counter information.

Step 2: Configure a Flow Exporter

<b>
R1(config)# flow exporter R1-FLOW-EXPORTER
R1(config-flow-exporter)# destination 10.250.250.25
R1(config-flow-exporter)# source Ethernet0/1
R1(config-flow-exporter)# transport udp 2055
R1(config-flow-exporter)# template data timeout 300
</b>

In the configuration for step 2, a flow exporter is defined at address 10.250.250.25 on UDP port 2055. If left unspecified, the UDP port used by default on a Cisco device is 9995. Exported data will be sourced from interface Ethernet 0/1. The NetFlow template timeout is set to 300 seconds. NetFlow Version 9 will periodically export the template data so the NetFlow collector will understand what data is to be sent, and also export the data flow set for the template. The key advantage to Flexible NetFlow is that the user configures a flow record, which is effectively converted to a Version 9 template and then forwarded to the collector.

Step 3: Configure a Flow Monitor

<b>
R1(config)# flow monitor R1-FLOW-MONITOR
R1(config-flow-monitor)# exporter R1-FLOW-EXPORTER
R1(config-flow-monitor)# record R1-FLOW-RECORD
</b>

In the configuration for step 3, a flow monitor is defined that combines the flow exporter and the flow record into one process.

Step 4: Apply the Flow Monitor to an interface

<b>
R1(config)# interface Ethernet 0/0
R1(config-if)# ip flow monitor R1-FLOW-MONITOR input
</b>

Finally, in the configuration for step 4, the ip flow monitor command is applied for input packets so that the newly defined flow monitor can start to gather information about traffic flows entering the Ethernet 0/0 interface.
