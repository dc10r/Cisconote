<h2>Configuring VRF-Lite</h2>

 VRF is usually associated with a service provider running Multiprotocol Label Switching (MPLS) because the two work well together. In a provider network, MPLS isolates each customer’s network traffic, and a VRF is maintained for each customer. However, VRF can be used in other deployments without using Multiprotocol Label Switching (MPLS). VRF-lite is the deployment of VRF without MPLS. With the VRF-Lite feature, the Cisco router supports multiple VPN routing/forwarding instances in customer-edge devices. VRF-Lite allows a PE router to support two or more VPNs with overlapping IP addresses using one interface. VRF-Lite uses input interfaces to distinguish routes for different VPNs and forms virtual packet-forwarding tables by associating one or more Layer 3 interfaces with each VRF.

Interfaces in a VRF can be either physical, such as Ethernet or serial ports, or logical, such as VLAN SVIs. However, a Layer 3 interface cannot belong to more than one VRF at any time.

<h3> PE Router Routing Contexts</h3>

Traditional Cisco IOS Software can support several different routing protocols. In some cases, even several completely isolated copies of the same routing protocol are supported. For example, several OSPF processes can be used.


For several important routing protocols, such as RIPv2, Enhanced Interior Gateway Routing Protocol (EIGRP), IS-IS, and BGP, Cisco IOS Software supports only a single copy of the protocol running in the router. These protocols cannot be used directly between Provider Edge (PE) and Custom Edge (CE) routers in VPN environments because each VPN (or, more precisely, each VRF) needs a separate, isolated copy of the routing protocol to prevent undesired route leakage between VPNs. Furthermore, VPNs can use overlapping IP address spaces (for example, each VPN could use subnetworks of network 10.1.1.0/24) that would also lead to routing confusion if all VPNs shared the same copy of the routing protocol.


<h3>VPN-Aware Routing Protocols</h3>


Routing contexts were introduced in Cisco IOS Software to support the need for separate isolated copies of VPN routing protocols. Routing contexts can be implemented as separate routing processes (in OSPF), similar to a traditional Cisco IOS Software implementation, or as separate isolated instances of the same routing protocol.

In VPN routing:

<ul>
  <li>A routing context is a routing protocol instance running in a VRF.</li>
  <li>VPN-aware routing processes include EBGP, EIGRP, OSPF, RIPv2, IS-IS, and static routes.</li>
  <li>VPN-aware routing processes include EBGP, EIGRP, OSPF, RIPv2, IS-IS, and static routes.</li>
</ul>

If routing contexts are implemented as instances of the same routing protocol, each instance contains its own independent routing protocol parameters. Examples would include networks over which the routing protocol is run, timers, authentication parameters, passive interfaces, and neighbors. This independence allows the network designer to have maximum flexibility in implementing routing protocols between PE and CE routers.


<h3> VRF Table</h3>

The major data structure that is associated with MPLS VPN implementation on Cisco platforms is the VRF table.

Virtual routing and forwarding:

A VRF is a routing instance for a set of sites with identical connectivity requirements.

A VRF table contains the following data structures:


<ul>
  <li>An IP routing table</li>
  <li>A CEF table</li>
  <li>A set of rules and routing protocol parameters</li>
  <li>A list of interfaces that use the VRF</li>
</ul>
A VRF table is associated with a route distinguisher and a set of import and export route targets.

The VRF data structure encompasses these constructs:

<ul>
  <li>An IP routing table that is identical in function to the global IP routing table in Cisco IOS Software</li>
  <li>A Cisco Express Forwarding table that is identical in function to the global Cisco Express Forwarding table (FIB)</li>
  <li>Specifications for routing protocols running inside the VRF instance</li>
</ul>

A VRF is a routing and forwarding instance that you can use for a single VPN site or for many sites connected to the same PE router, if and only if these sites share the same connectivity requirements.

<ul>
  <li>The RD, that is prepended (for example, RD + IP address) to all routes that are exported from the VRF into the global VPNv4 (also called VPN IPv4) BGP table</li>
  <li>A set of export RTs, that is attached to any route that is exported from the VRF</li>
  <li>A set of import RTs, that is used to select VPNv4 routes that are to be imported into the VRF</li>
</ul>

VRF table characteristics:

<ul>
  <li>Contains routes for a particular set of sites</li>
  <li>Similar to a standard routing table: Same set of mechanisms and rules</li>
  <li>Interfaces assigned to VRFs:</li>
       <ul>
  		<li>Many interfaces per VRF</li>
		<li>Physical, subinterfaces, or logical interfaces</li>
  		<li>Each interface can be assigned to only one VRF</li>
	</ul>
</ul>

The routes that are received from VRF routing protocol instances or from dedicated VRF routing processes are inserted into the IP routing table that is contained within the VRF. This IP routing table supports the same set of mechanisms as the standard Cisco IOS Software routing table. These mechanisms include filter mechanisms (distribute lists or prefix lists) and interprotocol route-selection mechanisms (administrative distances).

The per-VRF FIB table is built from the per-VRF routing table. This table is used to forward all the packets that are received through the interfaces that are associated with the VRF. Any interface can be associated with a VRF, whether it is a physical interface, subinterface, or logical interface, as long as it supports Cisco Express Forwarding switching.

There is no limit to the number of interfaces that can be associated with one VRF (other than the number of interfaces that are supported by the router). However, each interface can be assigned to only one VRF because the router needs to uniquely identify the forwarding table to be used for packets that are received over an interface.

<h2>VRF-Lite Functionality</h2>

VRF-Lite provides the ability to configure and maintain more than one VRF instance within the same PE router.

VRF-Lite features:

Support for multiple routing domains on a single PE router.

Each routing domain has its own:

Routing and forwarding table (VRF)

Set of interfaces

Multiple customers can share one PE.

Only one physical link is used between the CE and the PE.

VRF-Lite interfaces must be Layer 3 interfaces.

VRF-Lite uses input interfaces to distinguish routes for different VPNs and forms VRF tables by associating one or more Layer 3 interfaces with each VRF. Interfaces in a VRF can be either physical, such as Ethernet ports, or logical, such as VLAN SVIs. However, a Layer 3 interface cannot belong to more than one VRF at any time. The VRF-Lite feature thus allows an operator to support two or more routing domains on a router, with each routing domain having its own set of interfaces and its own set of routing and forwarding tables. The example in the topology demonstrates a PE router configured with two VRFs, using separate L3 interfaces to connect to CE1 and CE2, but using the same IP subnet. This is possible since each VRF has its own separate, isolated routing table.

VRF-Lite includes these devices:

Customer edge devices: CE devices provide customer access to the service provider network over a data link to one or more PE routers. The CE device advertises the local routes of the site to the PE router and learns the remote VPN routes from it.

Provider edge routers: PE routers exchange routing information with CE devices by using static routing or a routing protocol such as BGP, RIPv2, OSPF, or EIGRP. The PE router is only required to maintain VPN routes for the VPNs to which it is directly attached, eliminating the need for the PE router to maintain all the service provider VPN routes. Each PE router maintains a VRF for each of its directly connected sites. Multiple interfaces on a PE router can be associated with a single VRF if all these sites participate in the same VPN. Each VPN is mapped to a specified VRF. After learning local VPN routes from CE devices, a PE router exchanges VPN routing information with other PE routers by using IBGP.

<h2>Implement VRF-Lite</h2> 

With VRF-Lite, multiple customers can share one CE, and only one physical link is used between the CE and the PE. The shared CE maintains separate VRF tables for each customer and switches or routes packets for each customer, based on its own routing table. VRF-Lite extends limited PE functionality to a CE device, giving it the ability to maintain separate VRF tables to extend the privacy and security of a VPN to the branch office.

To understand the VRF-Lite configuration, you can look at a configuration of the CE and PE routers in a sample network. First, VRFs must be configured on both the PE and the CE routers. Also, you must specify the Layer 3 interface to be associated with the VRF and associate the VRF with.

If the CE router is only connected to one customer and only one routing context is required for that customer, then the CE router does not need to be VRF-aware or have VRFs configured locally. Only the PE router required the VRF configuration, since it is often shared among multiple clients.

For simple VRF-Lite deployments, RDs and RTs are not required. They only become necessary when BGP is used for inter-VRF route leaking.

<h2>Migration from Old to New Style VRF CLI</h2>

The multiprotocol VRF configuration allows you to define multiple address families under the same VRF. A given VRF, identified by its name and a set of policies, can apply to both an IPv4 VPN and an IPv6 VPN at the same time. This VRF can be activated on a given interface, even though the routing and forwarding tables are different for the IPv4 and IPv6 protocols.

Cisco IOS supports old and new VRF CLI formats:

Old Cisco IOS VRF configuration style that supports IPv4 only.

New multiprotocol IPv4 and IPv6 CLI

Migration tool from IPv4-only to multiprotocol VREF CLI

<b>
Router(config)# vrf upgrade-cli multi-af-mode {common-policies | non-common-policies} [vrf vrf-name]
</b>

<b>
Old Style VRF CLI
ip vrf CustomerA
rd 1:210
route-target both 1:210
!
interface Ethernet 0/0
ip vrf forwarding CustomerA
ip address 10.1.1.1 255.255.255.0
</b>

<b>
New Style VRF CLI
vrf definition CustomerA
rd 1:210
route-target both 1:210
!
address-family ipv4
exit-address-family
!
interface Ethernet 0/0
vrf forwarding CustomerA
ip address 10.1.1.1 255.255.255.0
</b>

Cisco IOS releases earlier than 12.2(33)SRB supported only the single-protocol IPv4-only VRF. You created a single-protocol VRF by entering the <b>ip vrf</b> command. To activate the single-protocol VRF on an interface, you enter the <b>ip vrf forwarding (interface configuration)</b> command. After the introduction of the VRF CLI for IPv4 and IPv6 VPNs feature in Cisco IOS Release 12.2(33)SRB, you can create a multiprotocol VRF by entering the vrf definition command. To activate the multiprotocol VRF on an interface, you enter the vrf forwarding command.

Cisco IOS offers a migration tool that upgrades a VRF instance or all VRFs configured on the router to support multiple address families under the same VRF. The <b>vrf upgrade-cli multi-af-mode {common-policies | non-common-policies} [vrf vrf-name]</b> command is issued in the configuration mode and uses these parameters:

The <b>multi-af-mode</b> keyword specifies an upgrade of the single-protocol VRF to the multiprotocol VRF that supports configuration of multiple address families.

The <b>common-policies</b> keyword specifies copying the route-target policies to the common part of the VRF configuration so that the policies apply to all address families configured in the multiple address family VRF.

The <b>non-common-policies</b> keyword specifies copying the route-target policies to the IPv4 address family part of the VRF configuration so that the policies apply only to IPv4.

The <b>vrf</b> keyword specifies a VRF for the upgrade to a multiple address family VRF configuration.

The <b>vrf-name</b> argument is the name of the single-protocol VRF to upgrade to a multiple address family VRF configuration.

The BGP and SHARED VRFs are configured with route distinguishers (RD) and route targets (RT) since these VRFs will be used with MP-BGP. Recall that RDs allow BGP to advertise and distinguish between duplicate IPv4 prefixes by applying a 64-bit value to the 32-bit IPv4 prefix. The RD can take one of three formats:

2-byte-integer:4-byte-integer

4-byte-integer:2-byte-integer

4-byte-dotted-decimal:2-byte-integer

In all three cases, the first value (before the colon) should be either an Autonomous System Number (ASN) or an IPv4 address. The second value, after the colon, can be any value.

Route targets determine into which VRFs a PE router places BGP-learned routes. In this scenario, you want to export and import routes between the BGP and SHARED VRFs using MP-BGP. Think of the term export to mean “redistribute out of the VRF into BGP” and the term import to mean “redistribute into the VRF from BGP.” Notice that routes from the SHARED VRF are being exported out and then imported into the BGP VRF, and vice versa. This configuration will for the implementation of inter-VRF route leaking which will be explored in Task 4.

The SHARED VRF is only configured with the IPv4 address family for simplicity.

On ISP, use the ping vrf command to test connectivity to each customer router.
<b>ISP# ping vrf OSPF 192.168.10.10</b>

Since each customer router is assigned to a specific VRF, it is important to source the ICMP echo request from the correct VRF. The <b>ping vrf</b> command allows the router to perform a VRF-aware ping. All ping tests should be successful.

<h4>Enable VRF-Lite Routing on the ISP Router</h4>

In this task, you will enable routing on the ISP router to support all four customer scenarios:

OSPFv3

EIGRP

MP-BGP

Static routing

On ISP, create an OSPFv3 process using process ID 10. Apply a router ID of 1.1.1.1. Configure IPv4 and IPv6 address families and assign them to the OSPF VRF.


<b>

ISP(config)# router ospfv3 10
ISP(config-router)# router-id 1.1.1.1
ISP(config-router)# address-family ipv4 unicast vrf OSPF
ISP(config-router-af)# exit
ISP(config-router)# address-family ipv6 unicast vrf OSPF
</b>
The OSPF VRF is assigned to the IPv4 and IPv6 address families of the OSPFv3 routing process.


On ISP, assign the Ethernet 0/0.10 interface to Area 0 and assign the loopback 0 interface to Area 1. Apply this configuration to both address families. Change the OSPF network type of the loopback 0 interface to point to point.


<b>
ISP(config)# interface Ethernet 0/0.10
ISP(config-subif)# ospfv3 10 ipv4 area 0
ISP(config-subif)# ospfv3 10 ipv6 area 0    
ISP(config-subif)# exit
ISP(config)# interface Loopback 0
ISP(config-if)# ospfv3 10 ipv4 area 1
ISP(config-if)# ospfv3 10 ipv6 area 1
ISP(config-if)# ospfv3 network point-to-point
<b>


OSPFv3 neighbor adjacency messages should appear for both IPv4 and IPv6 address families after enabling OSPF on the Ethernet 0/0.10 subinterface.

Enabling the point to point OSPF network type on the loopback 0 interface ensures that the ISP router advertises the correct subnet mask for that prefix (/24 instead of /32).

On ISP, verify the OSPF VRF IPv4 and IPv6 routing tables and test connectivity to the loopback 0 interface on the OSPF Customer router. Source the ping from the ISP loopback 0 interface.

VRFs are not configured locally on the OSPF Customer router. Instead, the global routing table shows that the router is learning an IPv4 and an IPv6 OSPF inter-area prefix from ISP.

<h4><Configure Inter-VRF Route Leaking on the ISP Router/h4>

In this task, you will configure the ISP router to leak routes between the BGP and SHARED VRFs. This will allow the EBGP Customer to reach the 203.0.113.1 public address hosted by the ISP router.

On ISP, configure a new IPv4 address family under the BGP process. Assign the SHARED VRF to it. Redistribute connected interfaces.
<b>

ISP(config)# router bgp 10
ISP(config-router)# address-family ipv4 unicast vrf SHARED
ISP(config-router-af)# redistribute connected
</b>


Since the Loopback 203 interface is already assigned to the SHARED VRF on the ISP router, redistributing connected interfaces allows BGP to advertise the prefix. Recall that route targets were configured to export SHARED VRFs prefixes and import them into the BGP VRF, and vice versa.
On the EBGP_CUST router, use the show bgp ipv4 unicast command to inspect the BGP table.
<b>
EBGP_CUST# show bgp ipv4 unicast 
</b>
Notice that the EBGP Customer router has learned the 203.0.113.1/32 prefix. This prefix is being exported out of the SHARED VRF and imported into the BGP VRF. ISP is then able to advertise it to the EBGP Customer router. The ?“” symbol at the end of the line is an indication that the origin of the prefix is unknown since it was redistributed on the ISP router.

On ISP, use the show bgp vpnv4 unicast all command to verify the BGP tables for all the VRFs.

<b>
ISP# show bgp vpnv4 unicast all
</b>
All prefixes are being imported and exported between the BGP and SHARED VRFs. There should be full connectivity between the two.

On the EBGP_CUST router, test connectivity to the Loopback 203 interface on the ISP router. Source the ping from the loopback 0 interface.
<b>
EBGP_CUST# ping 203.0.113.1 source Loopback 0
</b>
The EBGP Customer router can reach the public-host IP address 203.0.113.1 on the ISP router.
