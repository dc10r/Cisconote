<h2>IMPLEMENTING DMVPN</h2>

<h3>Overview of Cisco IOS DMVPN</h3>


DMVPN provides fully meshed connectivity with simple configuration of hub and spoke:

Supports dynamically addressed spokes

Facilitates zero-touch configuration for addition of new spokes

Features automatic IPsec triggering for building an IPsec tunnel


DMVPN allows IPsec VPN networks to better scale hub-to-spoke and spoke-to-spoke designs, therefore optimizing performance and reducing latency for communications between sites.

The following are the primary benefits of DMVPNs:

Hub router configuration reduction: Traditionally, configuration on the hub router defines the crypto map characteristics, the crypto Access Control List (ACL), and the GRE tunnel interface for each spoke router. The DMPVN feature enables users to configure a single mGRE tunnel interface and a single IPsec profile without requiring crypto ACLs on the hub router to manage all spoke routers. Thus, the size of the configuration on the hub router remains constant even if spoke routers are added to the network.

Automatic IPsec initiation: GRE uses Next Hop Resolution Protocol (NHRP) to configure and resolve the peer destination address. Thus, this feature allows IPsec to be immediately triggered to create point-to-point GRE tunnels without any IPsec peering configuration.

Support for dynamically addressed spoke routers: When you use point-to-point GRE and IPsec hub-and-spoke VPN networks, you must know the physical interface IP address of the spoke routers when you configure the hub router because the IP address must be configured as the GRE and IPsec tunnel destination address. DMVPN enables spoke routers to have dynamic physical interface IP addresses and uses NHRP to register the dynamic physical interface IP addresses of the spoke routers with the hub router.


With networks becoming geographically distributed, network availability over a secure channel is becoming a critical factor in designing scalable IPsec VPN solution designs. DMVPN solution architecture is by far the most effective and scalable solution available.

mGRE: mGRE technology enables a single GRE interface to support multiple GRE tunnels and simplifies the complexity of the configuration. GRE tunnels also provide support for IP multicast and non-IP protocols. IP multicast, in turn, enables the designer to use routing protocols to distribute routing information and detect changes in the VPN. All DMVPN members use GRE or mGRE interfaces to build tunnels between devices.


NHRP: NHRP is a client and server protocol in which the hub acts as an NHRP server and the spokes act as NHRP clients. The hub maintains an NHRP database of mappings between the outer (public, physical interface) and tunnel (inside the tunnel interface) IP addresses of each spoke. Each spoke registers its public and internal tunnel addresses when it boots and queries the NHRP database for the addresses of other spokes when building direct spoke-to-spoke tunnels. NHRP is used to reduce the configuration complexity of fully meshed or partially meshed VPNs into something that is comparable to the complexity of hub-and-spoke VPNs.

IPsec: IPsec provides transmission protection for GRE tunnels. DMVPNs form a permanent hub-and-spoke IPsec VPN, which can dynamically reconfigure itself into a partial mesh or full mesh as needed


A dynamic routing protocol is used to advertise private networks within the DMVPN networks. IP routing updates and IP multicast data packets traverse only hub-and-spoke tunnels. Unicast IP data packets traverse both hub-and-spoke and direct dynamic spoke-to-spoke tunnels. Routing adjacencies are established across the hub-to-spoke links, and the spoke-to-spoke routing logic is performed by NHRP. A routing protocol does not monitor the state of spoke-to-spoke tunnels. Protocols that are supported include RIP, EIGRP, OSPF, ODR, and BGP.

A DMVPN cloud topology can support either a hub-and-spoke or a spoke-to-spoke deployment model.

Hub-and-spoke: A strict hub-and-spoke DMVPN deployment model requires each branch to be configured with a point-to-point GRE interface to the hub, in which all traffic between spoke networks must flow through the hub router. DMVPN provides scalable configuration to the hub router, but does not facilitate direct spoke-to-spoke communication.

Spoke-to-spoke: A spoke-to-spoke DMVPN deployment model requires each branch to be configured with an mGRE interface in which dynamic spoke-to-spoke tunnels are used for the spoke-to-spoke traffic. In this model, DMVPN provides a scalable configuration model for all involved devices, and also allows spoke devices to dynamically peer and establish optimal routing paths. Note that DMVPN will not immediately produce a partially meshed or fully meshed topology. DMVPN initially establishes a permanent hub-and-spoke topology, from which a partial mesh, or full mesh is dynamically generated, based on traffic patterns.

Because VPNs are used for secure enterprise communications across a shared public infrastructure, such as the Internet, you must consider the following two distinct IP address domains:

The enterprise addressing space, sometimes referred to as the private or inside addresses: These are the addresses that are assigned to mGRE tunnel interfaces, and are registered to the hub NHRP server by each spoke.


The infrastructure addressing space, also referred to as the service provider, public, or outside addresses: These are the addresses on physical interfaces of the routers, and are used as addresses in the tunnel envelopes (that is, the source and destination addresses in the GRE/IPsec packet headers).

<h3>Understanding GRE</h3>

GRE is a simple, general-purpose protocol that is designed to manage the transportation of multiprotocol and IP multicast traffic between two or more sites, which may only have IP connectivity.

GRE uses IP protocol 47 and can be used with IPsec VPNs to pass routing information between connected networks. Tunneling protocols encapsulate packets inside a transport protocol. A tunnel interface supports a header for each of the following:

A passenger protocol or encapsulated protocol: This is the original IP packet in the diagram.

A carrier protocol: This is the GRE header in the diagram.

A transport protocol: This is the new IP header in the diagram.


The GRE header includes a flag field that identifies the presence of optional header fields, such as the tunnel checksum, the tunnel key, and the tunnel packet sequence number. The Protocol Type field identifies the type of passenger payload inside the GRE packet. For IPv4, the EtherType value is 0x0800. For IPv6, the value is 0x86DD.


GRE may be combined with IPsec, where GRE encapsulates the plaintext packet, and then IPsec cryptographically envelopes the packet. The diagram shows a GRE packet encapsulated by ESP in both tunnel mode and transport mode. Tunnel mode adds an extra IP header, whereas transport mode reuses the IP header from GRE. This is an economy of 20 bytes to the total packet size.

IPsec encapsulates unicast IP packet (GRE):

Tunnel mode (default): IPsec creates a new tunnel IP packet
Transport mode: IPsec reuses the IP header of the GRE (20 bytes less overhead)

GRE offers many useful features. Many vendors support GRE, so interoperability is usually not a problem when using basic GRE point-to-point connectivity. GRE tunnels support multiple network protocols, including IP multicasting. Multipoint tunneling is possible with GRE. A significant advantage of GRE tunneling relative to non-virtual tunnel interface (non-VTI) IPsec tunnels is that GRE uses Cisco IOS Software interfaces, which can offer finer-grained QoS features.

Some limitations of GRE tunneling include the following:

GRE provides no cryptographic traffic protection and must be combined with IPsec to provide it.

There is no standard method to determine the end-to-end state of a GRE tunnel or maintain GRE tunnels. Cisco IOS Software supports proprietary GRE keepalives for this purpose. Dynamic routing protocols are typically used to verify the end-to-end tunnel state.

It may be CPU-intensive on some platforms.

Tunnels can exhibit Maximum Transmission Unit (MTU) and IP fragmentation-related issues.

Most systems installed today leave the default MTU value set to 1500 and generate packets at this MTU size limit. The tunneling system tries to add the 24-bit GRE header onto the packet and this makes the packet too large for the MTU size. The tunneling system then begins to fragment the packets so they will fit under the MTU limit. Where this becomes an issue is when the DF bit is set and the tunneling systems fragment the packet. Once fragmented, some applications cannot process the packets, and this can cause problems. This also becomes an issue when a device wants to send an ICMP packet out to have the sending system retransmit the packets at a smaller size, but Internet Control Message Protocol (ICMP) is blocked before reaching the transmitting system (for example, a firewall blocks all ICMP messages).

<h3>NHRP</h3>

NHRP provides a mechanism to dynamically learn the IP addresses of the spokes.

A client-server protocol: the hub acts as the server and spokes are clients.

The hub maintains a database of all external (physical) and internal (tunnel) addresses of the spokes.

Each spoke registers its addresses when it boots.

NHRP is used by routers to determine the IP address of the next hop (in this case, the inner and outer IP addresses of spoke routers) in IP tunneling networks. When a spoke router initially connects to a DMVPN network, it registers its inner (tunnel) and outer (physical interface) address with the hub router (the NHRP server) whose IP address is statically preconfigured on the spoke router. This registration enables the mGRE interface on the hub router to build a dynamic GRE tunnel back to the registering spoke router without having to know the branch tunnel destination in advance. Therefore, NHRP creates a mapping for a tunnel IP address to the physical interface IP address for each spoke at the hub.

NHRP is a client-server protocol: the hub acts as the server and the spokes are clients. You must configure spoke routers with the physical interface IP address of the hub router as their next-hop server in order for spokes to register with the hub router. The spoke routers send an NHRP registration to the hub router that contains their tunnel IP address and the physical interface IP address. The hub router creates an entry in its NHRP cache and returns a registration reply. The spoke router now views the hub router as a valid next-hop server and uses it as a source to locate any other spokes and networks in the NHRP domain. From the routing protocol perspective, the NHRP domain operates similarly to an NBMA network.

(m)GRE-NHRP Integration

mGRE (and IPsec in DMVPN) uses NHRP to create dynamic tunnels.

The hub learns the spoke addresses to create GRE tunnels to them.

Spokes query the server to resolve external addresses of other spokes and create dynamic GRE tunnels to them.


Using NHRP in multipoint GRE networks maps inner-tunnel IP addresses to the outer transport IP addresses. In a hub-and-spoke DMVPN deployment, no GRE or IPsec information about a spoke is configured on the hub router. The spoke router for the GRE tunnel is configured (via NHRP commands) with information about the hub router as the next-hop server. When the spoke router starts up, it automatically initiates the IPsec tunnel with the hub route. It then uses NHRP to notify the hub router of its current physical interface IP address. This notification is useful for the following reasons:

Configuration of the hub router is shortened and simplified because it does not need to have GRE or IPsec information about the peer routers. All this information is learned dynamically via NHRP.

When you add a new spoke router to the DMVPN network, you do not need to change the configuration on the hub or on any of the current spoke routers. The new spoke router is configured with the hub information, and when it starts up, it dynamically registers with the hub router. The dynamic routing protocol propagates the routing information for this spoke to the hub. The hub propagates this new routing information to the other spokes. It also propagates the routing information from the other spokes to the new spoke.

In the figure, one spoke wants to send IP traffic to another spoke, which has a tunnel interface that is configured with the IP address of 10.1.1.3. The originating router sends an NHRP query for the 10.1.1.3 IP address to the hub, which is configured as an NHRP server. The hub responds with information that the IP address 10.1.1.3 is mapped to the physical interface (172.17.3.34) of the receiving spoke router.

<h3>DMVPN Operations</h3>

DMVPN Initial State

Initially, all spokes register with the hub:

Hub has a static physical IP address.

Spokes can be statically or dynamically (physically) addressed.

NHRP mappings are created.

Spoke-to-hub GRE and IPsec tunnels are created.

All traffic from the spoke is forwarded.

The figure illustrates a DMVPN example, where the top (hub) router is used as DMVPN hub and other two routers are statically configured to connect to the hub using NHRP, GRE, and IPsec. The VPN tunnels between the spokes are not permanent, but are established on demand. Initially, all spokes establish a GRE/IPsec tunnel with the hub and NHRP-register with the hub.

At this point, the network is strictly hub-and-spoke and can remain that way, if so configured. The following are the current network properties:

The hub knows the outer and inner IP addresses of each spoke in its NHRP database.

Two spoke-to-hub GRE/IPsec tunnels are created.

All traffic from each spoke (to the hub networks or to the networks of other spokes) is forwarded via the hub.

Dynamic Spoke-to-Spoke Tunnel Creation: A PC (192.168.2.10) inside the left spoke network wants to communicate with a server (192.168.3.10) inside the right spoke network. It sends a packet toward the server.

In a spoke-to-spoke-enabled DMVPN, spokes can dynamically locate each other and establish direct tunnels.


This figure illustrates dynamic spoke-to-spoke tunnel creation when a packet is sent from the left spoke site to the right spoke site. In this figure, static NHRP-enabled GRE tunnels are already configured and pre-established from the hub to all spokes. A PC (192.168.2.10) on the left spoke subnet wants to connect to a web server (192.168.3.10) behind the right spoke router. It sends a packet towards the server.

The left spoke router finds the destination network (192.168.3.0/24) reachable over the 10.1.1.3 next hop on its mGRE interface.

Dynamic routing (running over the permanent hub-to-spoke links) is used to populate the routing table of the spoke, so each spoke knows about subnets behind other spokes. The left spoke router consults its routing table for a route to the destination network (192.168.3.0) and finds it reachable behind the right spoke router. The routing table provides an IP next-hop of 10.1.1.3 via the mGRE tunnel interface of the left spoke router.

The left spoke router does not find a mapping for the 10.1.1.3 next hop in its NHRP cache and consults the NHRP server.

After consulting its local NHRP cache for the 10.1.1.3 next hop and finding no cached entries, the left spoke router sends an NHRP query to the NHRP server (DMVPN hub) to resolve the inner (private) tunnel address 10.1.1.3 to an outer (physical, public) tunnel endpoint address.

The hub resolves the 10.1.1.3 tunnel next hop to the 172.17.3.34 physical interface address of the right spoke (based on its NHRP registration).

The NHRP server (hub) stores information about the inner (tunnel) and outer (physical) addresses of all spoke routers based on the NHRP registration information that is received from the initial registration of the spokes to the hub. It sends an NHRP reply to the left spoke informing it that the 10.1.1.3 next hop is reachable through the 172.17.3.34 outer (physical) IP address of the right spoke router.

The response triggers the creation of a dynamic GRE/IPsec tunnel between spoke physical addresses. The answer from the NHRP server is cached on the spoke.

The left spoke receives the NHRP response from the DMVPN hub (the NHRP server) and enters it in the local NHRP cache. This triggers IPsec on the left spoke to create an IPsec tunnel directly to the right spoke, reachable at 172.17.3.34. The left spoke initiates an Internet Key Exchange (IKE) session to 172.17.3.34, using its physical IP address (172.17.2.24) as the source, and negotiates IPsec SAs for a spoke-to-spoke GRE tunnel.

Now that the tunnel has been built, traffic can flow directly between the left spoke network and the right spoke network. Note that traffic cannot flow directly in the other direction yet.

After the IPsec tunnel is created, the left spoke will create a GRE tunnel to 172.17.3.34, and all subsequent packets from the left spoke network and the right spoke network will bypass the hub. This solution has the performance benefit of relieving the hub from decrypting and encrypting these packets, and also reduces the impact on the hub link. Note that, at this point, the spoke-to-spoke tunnel can pass traffic in one direction only, from the left spoke to the right spoke.

When the web server replies to client traffic, the same sequence of NHRP and GRE/IPsec processes occurs. Because there is already a GRE/IPsec tunnel in place, a duplicate tunnel is avoided.

To provide bidirectional connectivity, the right spoke router also needs next-hop information for the left spoke router from the NHRP server. The right spoke router sends an NHRP query when the first packet needs to be forwarded from a host in the right spoke network to the network behind the left spoke router. When the right spoke router has the NHRP mapping for the left spoke router, the corresponding GRE association is built, and a response packet is sent directly to the left spoke router, encapsulated in a GRE/IPsec tunnel. The IPsec tunnel, however, is already in place and is not duplicated.

After a configurable timeout value, NHRP entries on the spoke routers time out, causing the dynamic spoke-to-spoke tunnel to be torn down.

The designer may want to tune (lower) the IPsec SA and NHRP timers to prevent too many lingering tunnels after there is no more traffic between spokes. After a timeout period, the NHRP entries will age out, triggering IPsec to break down the dynamic spoke-to-spoke tunnel because it is no longer needed.


<h3>DMVPN Authentication</h3>

There are two types of DMVPN authentication:

Preshared keys

PKI-based IKE authentication

Consider the following when implementing DMVPN:

In a hub-and-spoke DMVPN, either authentication type is acceptable.

In fully meshed DMVPNs, PKI-based authentication is highly recommended.

When configuring DMVPN, you will have to make some deployment choices. In a strict hub-and-spoke DMVPN, choose either PSKs or PKI-based IKE authentication, both are acceptable. In fully meshed DMVPNs, PKI-based authentication is highly recommended.

Pre-shared keys are easy to deploy and highly scalable, but they become very difficult to manage. Any DMVPN peer with the knowledge of the password can establish a DMVPN session to the headend in a pre-shared key environment. Moreover, if there are multiple headends then the passwords must be synchronized between the headends—which makes it inherently more difficult to manage. If spoke-to-spoke communication is required, then you must maintain passwords between the spokes. Taken together, these issues can confuse the process of securing a large deployment. To avoid this, some organizations can use wild card-based strategy for authentication, which involves matching any IP address with one password. This can create security risk for the solution. Another weakness in pre-shared key-based security is the difficulty in removing spokes off the network. Removing spokes requires the removal of each associated pair-wise password from the headends or the spokes.

PKI addresses all the issues encountered with a pre-shared key authentication strategy. The significant benefits of PKI solutions including the following:

PKI supports hierarchical architectures, therefore scaling to large number of sessions.

PKI is highly secure because it uses public key cryptography.

PKI is easier to manage; certificates can be added, deleted, or revoked.

PKI can be used to provide better security for VPN connections such as DMVPN. The figure depicts how PKI can be used in a branch/WAN deployment. A key design consideration is locating the CA server. Because all the branches must enroll with the CA server, it should be directly accessible on the WAN edge, as should the DMVPN gateway.

<h3>DMVPN Hub Configuration</h3>


These steps represent the DMVPN hub configuration sequence:

1 (Optional) First, you can configure an IKE policy to interface with other IPsec peers. If you do not configure a specific policy, the hub will use default IKE policies.

2 Generate or configure authentication credentials to authenticate spoke devices. Typically, you will enroll the hub into a PKI to obtain a certificate for this purpose.

3 Configure an IPsec profile. and inside the profile, an optional IPsec transform set. If you do not configure a transform set, the router will use default IPsec transform sets. An IPsec profile, however, is mandatory, even if it is empty.

4 Create an mGRE tunnel interface.

5 Configure NHRP server parameters inside the mGRE tunnel interface.

6 Inside the mGRE tunnel interface, configure tunnel protection, referencing the IPsec profile.

7 Inside the mGRE tunnel interface, configure all required and optional IP parameters. (IP address, IP fragmentation and TCP segmentation parameters)

(Optional) Configure an IKE policy to interface with the hub and other spokes. If you do not configure an IKE policy, the spoke will use default IKE policies.

Generate or configure authentication credentials to authenticate the hub and other spoke devices. Typically, you will enroll the spoke into a PKI to obtain a certificate for this purpose.

Create mGRE tunnel interface.

Configure NHRP client parameters inside the mGRE tunnel interface.

Inside the mGRE tunnel interface, configure tunnel protection. (Associate the IPsec profile with the mGRE interface.)

Inside the mGRE tunnel interface, configure all required and optional IP parameters. (IP address, IP fragmentation, and TCP segmentation parameters)

<h3>DMVPN Routing Configuration</h3>


Routing protocols usually need additional configuration.

The DMVPN cloud is an Nonbroadcast Multiaccess (NBMA) network.

Routing protocol peering occurs only between the spoke and the hub.

Tuning the routing protocol on the hub specifies whether the network will be hub-and-spoke or a full mesh.

Some considerations must be made when running dynamic routing protocols across the DMVPN, especially when you are implementing a spoke-to-spoke design, because the DMVPN cloud is like an NBMA network. Many routing protocols have an IP multicast mechanism that is used to discover other participating nodes. For this purpose, you must configure NHRP multicast maps on spoke routers to register this capability with the hub. You configure the hub router with a dynamic multicast map that will replicate multicast packets to all spokes. This configuration allows the hub and spokes to exchange multicast and broadcast information, but does not permit spokes to receive broadcasts from other spokes.

In a DMVPN, routing protocol peering (neighbor relationships) occurs only between each spoke and the hub. There is never spoke-to-spoke peering. Therefore, the hub will pass information about all spoke networks to other spokes.

It is important to note that the tuning of the routing protocol functions on the hub is the main factor that will determine whether your DMVPN will operate in strict hub-and-spoke or partially meshed or fully meshed topology. The only other factor is the choice of the GRE interface for the spokes: a point-to-point GRE interface on the spoke will only allow a strict hub-and-spoke topology, while a mGRE interface on the spokes will allow the use of both topologies.

You can use EIGRP to deploy either a strict hub-and-spoke DMVPN, or a partially meshed or fully meshed DMVPN.

EIGRP deployment is straightforward in a strict hub-and-spoke DMVPN deployment. You should typically disable automatic summarization on the hub, and disable the EIGRP split-horizon feature in order for the hub to propagate spoke network information to other spokes, because they are reachable over the same mGRE interface.

Spoke-to-spoke, partially meshed, or fully meshed DMVPN networks present a unique challenge because the spokes cannot directly exchange information with each other, even though they are on the same logical subnet. Note

As with all EIGRP networks, the number of neighbors should be limited to ensure that the hub router can re-establish communications after a major outage. If the DMVPN cloud is configured with a /24 network prefix, the neighbor count is limited to 254, which is a safe operational limit. Beyond this number, a compromise is required to balance reconvergence with recovery. In large EIGRP networks, it might be necessary to adjust the EIGRP holdtime to allow the hub more time to recover without thrashing.

Running OSPF over a DMVPN network has some of the same challenges as running OSPF over other types of networks. Because only the hub is in direct communications with all branches, it should be configured as the DR on the DMVPN subnet. There is not typically a BDR for this type of configuration. A BDR is possible if a second hub is placed on the same subnet.

In strict hub-and-spoke DMVPNs, you should include the tunnel interface in the OSPF routing process, and configure the tunnel interface as a point-to-multipoint OSPF network type on the hub router, and as a point-to-point network type on the branch routers. In this case, there is no need to elect a DR on the DMVPN subnet. The hub router serves as the primary for the subnet. The branches consider the hub as the only path off the subnet, thus simplifying the Dijkstra's algorithm for the OSPF area. Use a suitable OSPF priority to ensure that the hub is always elected as the DR.

To create a partially meshed or fully meshed DMVPN, configure the mGRE tunnel on the hub router as an OSPF broadcast network. Each spoke router should be configured with an OSPF priority of 0 to prevent a spoke from becoming a DR or BDR. The tunnel IP MTU must match on all of the GRE interfaces that are OSPF-adjacent. In addition, OSPF areas running over DMVPN can be not-so-stubby or totally stubby areas to reduce LSA flooding over the WAN.

Verifying the State of GRE Tunnels

Line protocol on a GRE tunnel interface is up if there is a route to the tunnel destination (unless you configure GRE keepalives).

Line protocol on an mGRE tunnel interface is always up.

Verify GRE peering using ping to tunnel addresses, or by observing IGP neighborships (both require NHRP if mGRE is used).

Verifying the State of GRE Tunnels (Cont.)

After configuring a hub-and-spoke GRE tunnel, verify the state of it by using the <b>show interface tunnel<b> command. The line protocol on a GRE tunnel interface is up as long as there is a route to the tunnel destination, unless you configure GRE keepalives (which are not recommended if you will also use a dynamic routing protocol over the tunnel). The line protocol on an mGRE tunnel interface is always up.

You can quickly verify that a GRE tunnel is actually passing traffic by using the ping command and specifying the (inner) tunnel IP addresses of the remote GRE peer as target IP addresses. Another option is to observe if a routing protocol neighbor relationship establishes successfully over the tunnel (if you have configured a routing protocol). Again, both approaches require NHRP if mGRE is used.


Verifying NHRP Mappings

On the hub, you should see mappings for all registered spokes.

<b>Hub# show ip nhrp<b>

On a spoke, you should see a static mapping for the hub, a local mapping, and dynamic mappings for any spokes that the local spoke sends traffic to.

<b>Spoke# show ip nhrp</b>

On the hub (the NHRP server), you should see NHRP mappings for all registered spokes

On a spoke (the NHRP client), you should see a static mapping for the hub, a local mapping for the local spoke, and dynamic mappings for any spokes that the local spoke is sending traffic to

Debugging NHRP

On the spoke, the command below shows issues with NHRP registration (most likely a network ID or authentication key mismatch).

<b>Spoke# show ip nhrp nhs detail</b>

If the req-failed field displays a number greater than 0, this is a good hint that there is a network ID or authentication key mismatch, or a connectivity problem with the next-hop server.

This command shows the details of all spoke-to-hub tunnels:

<b>Hub# show dmvpn detail</b>


In the output, you should see entries for all connected spokes. The additional per-spoke information available is as follows:

The spoke NBMA address, on the physical interface or loopback, where tunnel is attached

The spoke tunnel address, as set on the spoke GRE or mGRE tunnel

The tunnel state, UP for successfully established tunnel

The tunnel uptime

The target network, which represents the NHRP client address of the spoke

The <b>show dmvpn detail</b> command will reveal additional information about DMVPN peers. In addition to information already displayed by show dmvpn, detailed output includes IKE SA information: local and remote IP addresses and IKE status. IPsec statistics will show the number of packets that the router has encrypted and decrypted. If these counters are not increasing and traffic is not flowing through the DMVPN, there could be a problem with IPsec SAs or routing.


Hub-and-Spoke Routing and IKE Peering (Spoke)

In hub-and-spoke networks, all routes to spoke networks should be reachable over the hub.

Only a single spoke-to-hub IKE session (IKE SA) should be present on the spoke.

<b>Spoke# show ip route eigrp</b>

Full-Mesh Routing and IKE Peering (Spoke)

In spoke-to-spoke networks, all routes to spoke networks should be reachable directly over the spoke.

IKE sessions should also be established with all other spokes to which traffic is currently being forwarded.

<b>Spoke# show ip route eigrp</b>

When verifying routing in strict hub-and-spoke DMVPNs, issue the show ip route command on a spoke to verify that all other spoke networks are routed through the hub. The next hop for each spoke prefix should be the tunnel (inner) IP address for the hub. You can also check that there is only one IKE SA and that it is established with the hub, by using the show crypto isakmp sa command.

When verifying routing in a partially meshed or fully meshed DMVPN, issue the show ip route command on a spoke and check that all spoke networks are routed directly toward the spokes, with the tunnel (inner) IP addresses shown as next hops for spoke prefixes. There should be an IKE session with the hub, and, potentially, IKE sessions with some other spokes as well, depending on with which spokes the local spoke is currently exchanging traffic.

<h3>Implement Cisco IOS DMVPN</h3>


<h4> Configure HQ as DMVPN Hub</h4>

<h4>Dynamic Multipoint VPN (DMVPN)</h4>

DMVPN provides complete connectivity while simplifying configuration as new sites are deployed. It is considered a zero-touch technology because no configuration is needed on the DMVPN hub routers as new spokes are added to the DMVPN network. This facilitates a consistent configuration where all spokes can use identical tunnel configuration (that is, can be templatized) to simplify support and deployment.

Spoke sites initiate a persistent VPN connection to the hub router. Network traffic between spoke sites does not have to travel through the hubs. DMVPN dynamically builds a VPN tunnel between spoke sites on an as-needed basis. This allows network traffic, such as for VoIP, to take a direct path, which reduces delay and jitter without consuming bandwidth at the hub site.

DMVPN was released in three phases, and each phase was built on the previous one with additional functions. All three phases of DMVPN need only one tunnel interface on a router, and the DMVPN network size should accommodate all the endpoints associated to that tunnel network. DMVPN spokes can use DHCP or static addressing for the transport and overlay networks. They locate the other spokes’ IP addresses (protocols and NBMA) through NHRP.

DMVPN tunnels can have IPsec enabled to secure the connectivity between sites.


<h4>Phase 1: Spoke-to-Hub</h4>

DMVPN Phase 1 was the first DMVPN implementation and provides a zero-touch deployment for VPN sites. VPN tunnels are created only between spoke and hub sites. Traffic between spokes must traverse the hub to reach the other spoke.


<h4> Phase 2: Spoke-to-Spoke</h4>

DMVPN Phase 2 provides additional capability from DMVPN Phase 1 and allows spoke-to-spoke communication on a dynamic basis by creating an on-demand VPN tunnel between the spoke devices. DMVPN Phase 2 does not allow summarization (next-hop preservation). As a result, it also does not support spoke-to-spoke communication between different DMVPN networks (multilevel hierarchical DMVPN).


<h3>Phase 3: Hierarchical Tree Spoke-to-Spoke</h3>


DMVPN Phase 3 refines spoke-to-spoke connectivity by enhancing the NHRP messaging and interacting with the routing table. With DMVPN Phase 3 the hub sends an NHRP redirect message to the spoke that originated the packet flow. The NHRP redirect message provides the necessary information so that the originator spoke can initiate a resolution of the destination host/network.

In DMVPN Phase 3, NHRP installs paths in the routing table for the shortcuts it creates. NHRP shortcuts modify the next-hop entry for existing routes or add a more explicit route entry to the routing table. Because NHRP shortcuts install more explicit routes in the routing table, DMVPN Phase 3 supports summarization of networks at the hub while providing optimal routing between spoke routers. NHRP shortcuts allow a hierarchical tree topology so that a regional hub is responsible for managing NHRP traffic and subnets within that region but spoke-to-spoke tunnels can be established outside of that region.

An IPsec transform set is configured using AES 256 for encryption and SHA 384 for data integrity. Transport mode is selected. IPsec can run in two modes, transport mode and tunnel mode. In transport mode, the original IP header is not encrypted and there is no additional IP header added. In tunnel mode, which is the default for tunnels, a new IP header is added, and the original IP header is encrypted. IPsec transport mode adds approximately 36 bytes, while tunnel mode adds approximately 52 bytes. When using DMVPN with IPsec, it is not desirable to use tunnel mode. DMVPN uses GRE which means that a new IP header is already added by GRE. The GRE encapsulation happens on the tunnel interface before the encryption process takes place. When using DMVPN and IPsec together, IPsec transport mode should be used to save on the overhead.

However, HQ is receiving OSPF hellos from multiple routers (BRANCH1 and BRANCH2). To fix this issue, change the OSPF network type to point-to-multipoint.


On the HQ router, enable OSPF Area 0 on the Tunnel 1 interface and Area 1 on the loopback 0 interface.

<b>
HQ(config)# router ospf 1
HQ(config-router)# network 10.1.1.0 0.0.0.255 area 0
HQ(config-router)# network 192.168.1.0 0.0.0.255 area 1
HQ(config-router)# exit 
HQ(config)# exit
</b>

On the BRANCH1 and BRANCH2 routers, configure the Tunnel 1 interface as an OSPF point-to-multipoint network.

<b>
BRANCH1(config)# interface Tunnel1
BRANCH1(config-if)# ip ospf network point-to-multipoint
BRANCH1(config-if)# exit

BRANCH2(config)# interface Tunnel1
BRANCH2(config-if)# ip ospf network point-to-multipoint
BRANCH2(config-if)# exit
</b>

On the BRANCH1 and BRANCH2 routers, enable OSPF Area 0 on the Tunnel 1 interface. Also, enable OSPF area 2 on the loopback 0 interface on BRANCH1 and enable OSPF area 3 on the loopback 0 interface on BRANCH2.

<b>
BRANCH1(config)# router ospf 1
BRANCH1(config-router)# network 10.1.1.0 0.0.0.255 area 0
BRANCH1(config-router)# network 192.168.2.0 0.0.0.255 area 2
BRANCH1(config-router)# exit 
BRANCH1(config)# exit
BRANCH2(config)# router ospf 1
BRANCH2(config-router)# network 10.1.1.0 0.0.0.255 area 0
BRANCH2(config-router)# network 192.168.3.0 0.0.0.255 area 3
BRANCH2(config-router)# exit
BRANCH2(config)# exit
</b>
After entering the OSPF commands on BRANCH1 and BRANCH2, console messages confirm the newly formed OSPF adjacency with HQ.

<h4>Enable DMVPN Phase 3 Functionality</h4>


The Phase 3 DMVPN configuration for the hub router adds the interface parameter command ip nhrp redirect on the hub router. This command checks the flow of packets on the tunnel interface and sends a redirect message to the source spoke router when it detects packets hairpinning out of the DMVPN cloud. Hairpinning is when traffic is received and sent out of an interface in the same cloud (identified by the NHRP network ID). For instance, packets coming in and going out of the same tunnel interface is a case of hairpinning.

The Phase 3 DMVPN configuration for spoke routers uses the multipoint GRE tunnel interface and uses the command ip nhrp shortcut on the tunnel interface.

In this task, you will enable DMVPN Phase 3 to improve spoke-to-spoke direct communication.


On the HQ router, enable NHRP redirect and change the OSPF network type of the Tunnel 1 interface to point-to-multipoint.

<b>
HQ(config)# interface Tunnel 1
HQ(config-if)# ip nhrp redirect
HQ(config-if)# ip ospf network point-to-multipoint 
</b>

It is recommended to use the OSPF network type point-to-multipoint when enabling DMVPN Phase 3 with NHRP redirect. Doing so will cause the OSPF neighbor adjacencies to temporarily go down as there is currently an OSPF network mismatch with BRANCH1 and BRANCH2.

On the BRANCH1 and BRANCH2 routers, enable NHRP shortcuts and change the OSPF network type of the Tunnel 1 interface to point-to-multipoint. Also, remove the OSPF priority command.

<b>
BRANCH1(config)# interface Tunnel 1
BRANCH1(config-if)# ip nhrp shortcut 
BRANCH1(config-if)# no ip ospf priority 0
BRANCH1(config-if)# ip ospf network point-to-multipoint 

BRANCH2(config)# interface Tunnel 1
BRANCH2(config-if)# ip nhrp shortcut 
BRANCH2(config-if)# no ip ospf priority 0
BRANCH2(config-if)# ip ospf network point-to-multipoint 
</b>
After enabling the point-to-multipoint OSPF network type on BRANCH1 and BRANCH2, the OSPF adjacencies with HQ are re-established.

On the BRANCH1 router, clear all crypto and GRE tunnels by disabling and re-enabling the Tunnel 1 interface. This ensures that all further tests are conducted in a fresh DMVPN Phase 3 environment. Verify the ISAKMP SA status after the OSPF neighbor adjacency with HQ is re-established.

</b>

<b>

</b>

BRANCH1 now has two ISAKMP SAs, one with HQ and one with BRANCH2. Traffic between BRANCH1 and BRANCH2 is being successfully encrypted/decrypted. The same applies for traffic between BRANCH1 and HQ.

On the BRANCH1 router, verify the status of NHRP.

<b>
BRANCH1# show ip nhrp
</b>

Notice the NHRP mappings: router, rib, and nho. The flag rib nho indicates that the router has found an identical route in the routing table that belongs to a different protocol. NHRP has overridden the other protocol’s next-hop entry for the network by installing a next-hop shortcut in the routing table. BRANCH1 is now using the 10.1.1.3 next-hop address to reach the 192.168.3.0/24 network on BRANCH2.

</b>

The output displays the status of DMVPN tunnels on BRANCH1 where there are two new spoke-to-spoke tunnels (highlighted). The DLX entry represents the local (no-socket) routes. The original tunnel to HQ remains as a static tunnel. The DT2 entry indicates that the next-hop has been overridden by NHRP.

On the BRANCH1 router, verify the OSPF routes in the routing table.

<b>
BRANCH1# show ip route ospf
</b>

NHRP tightly interacts with the routing/forwarding tables and installs or modifies routes in the Routing Information Base (RIB), also known as the routing table, as necessary. When an entry exists with an exact match for the network and prefix length, NHRP overrides the existing next hop with a shortcut. The original protocol is still responsible for the prefix, but the overwritten next-hop address is indicated in the routing table by the percent sign (%).

The next-hop IP address for the OSPF inter-area remote network (highlighted) still shows 10.1.1.1 as the next-hop address but includes a percent sign (%) to indicate a next-hop override.

On the BRANCH1 router, verify explicit NHRP shortcut information in the routing table.

<b>

</b>

The command show ip route next-hop-override displays the routing table with the explicit NHRP shortcuts that were added. In the output, notice that the NHRP shortcut is indicated by the NHO marking and shown underneath the original entry with the correct next-hop IP address.
